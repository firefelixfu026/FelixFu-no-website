# Vibe Coding 与 Agent 学习路线

## 总览

Vibe Coding 是以自然语言意图为入口、以大语言模型为生成引擎、以工程工具链为执行环境、以自动化验证为质量闭环的软件开发范式。Agent 是在此基础上进一步引入目标管理、状态维护、工具调用、反馈循环和多步骤执行能力的系统形态。

核心技术脉络可以抽象为：

```text
LLM 生成能力
  -> Function Calling / Tool Use
  -> Agent Loop
  -> MCP / Skill / Workflow
  -> RAG / Memory / SubAgent / Agent Team
  -> 可验证、可追踪、可协作的 AI Native 工程系统
```

人和模型的分工本质不是“AI 替代开发者”，而是重新分配工程劳动：

- **人负责目标与验收**：定义问题、明确边界、确定优先级、审查风险、决定取舍。
- **模型负责生成与加速**：生成代码、补全样板、解释错误、改写文档、提出候选方案。
- **工具负责真实执行**：读写文件、运行命令、执行测试、查询数据库、调用外部 API。
- **Agent 负责流程串联**：在目标、上下文、工具和反馈之间组织多步骤执行。

高质量 Vibe Coding 的关键不是“让模型写得更多”，而是建立确定性的工程约束：需求结构化、上下文可控、工具权限清晰、测试自动化、产物可审查。

## 如何做好 Vibe Coding

### 1. 大模型原理

LLM（Large Language Model）的生成机制建立在 token 序列建模之上。模型根据输入上下文计算下一个 token 的概率分布，再通过解码策略生成连续文本。代码同样是高度结构化的符号序列，因此模型可以学习函数签名、框架模式、错误处理、测试结构和文档格式之间的统计关联。

代码生成能力主要来自四类能力叠加：

- **语法模式学习**：模型学习编程语言的语法结构、常见库调用和项目组织方式。
- **语义关联压缩**：模型将自然语言需求、API 名称、变量命名和逻辑结构压缩到参数空间中。
- **上下文对齐**：模型根据当前文件、已有代码风格、错误日志和用户指令生成局部一致的输出。
- **指令跟随能力**：经过指令微调和偏好对齐后，模型能够按任务格式输出代码、解释、测试和文档。

幻觉产生的主要原因包括：

- **参数记忆不等于事实查询**：模型可能生成训练中常见但当前环境不存在的 API、配置项或命令。
- **上下文缺失**：未提供依赖版本、项目结构、已有约束时，模型会基于通用模式补全空白。
- **目标函数偏向流畅性**：生成文本的连贯性不保证事实正确性和运行正确性。
- **工具反馈不足**：未执行测试、未读取真实文件、未查询官方文档时，模型无法自动纠偏。
- **长链路误差累积**：多轮生成中早期错误会污染后续上下文，导致错误被包装成“合理解释”。

工程实践中，模型输出应被视为候选实现，而不是最终事实：

```text
模型输出 -> 静态检查 -> 单元测试 -> 集成测试 -> 人工 Review -> 合并
```

多模型协同用于降低单模型自证风险。常见分工如下：

- **代码生成模型**：负责快速生成实现、测试、脚手架和迁移代码。
- **代码审查模型**：从正确性、安全性、边界条件、性能、可维护性角度审查 diff。
- **文档生成模型**：把实现产物转化为 README、接口说明、变更日志和学习笔记。
- **研究检索模型**：基于官方文档、标准规范和版本说明核对 API 与最佳实践。

推荐协同流程：

1. 定义需求、约束和验收标准。
2. 生成模型产出最小候选实现。
3. 工具链执行格式化、类型检查、测试、构建。
4. 审查模型只读取 diff、测试结果和相关文件，输出风险清单。
5. 生成模型基于审查意见修复。
6. 人类开发者根据业务目标和工程风险做最终验收。

### 2. 开发工具大全

AI 编程工具链可以按接近真实工程环境的程度划分。

| 工具形态 | 典型工具 | 核心能力 | 适用场景 | 主要风险 |
| --- | --- | --- | --- | --- |
| Web Chat | ChatGPT、Claude、Gemini | 解释概念、生成草稿、方案讨论 | 学习、设计、文档草稿 | 缺少本地上下文，容易产生版本幻觉 |
| IDE AI 插件 | Cursor、Windsurf、GitHub Copilot、JetBrains AI | 代码补全、局部重构、上下文问答 | 日常编码、局部修改、快速跳转 | 容易局部最优，忽略跨模块影响 |
| CLI Agent | Codex、Claude Code 类工具 | 读写文件、执行命令、运行测试、修改项目 | 工程闭环、批量重构、测试修复 | 权限过大时可能误改文件 |
| 自动化平台 | Dify、Coze、n8n、LangGraph Studio | 可视化流程、RAG 应用、业务编排 | 快速原型、业务流程验证 | 状态复杂后调试困难 |
| 框架层 | LangChain、LangGraph、LlamaIndex、AutoGen、CrewAI | 模型调用、工具注册、状态管理、多 Agent 协作 | Agent 应用开发、研究实验 | 抽象成本和框架锁定 |

工具选择原则：

- 小范围代码补全优先使用 IDE 插件。
- 跨文件修改和测试修复优先使用 CLI Agent。
- 业务流程验证可使用低代码平台快速搭建。
- 需要稳定状态机、多步骤工具调用和多 Agent 协作时，引入代码框架。

MCP（Model Context Protocol）用于标准化模型应用与外部工具、数据源和提示模板之间的连接方式。它将外部能力暴露为统一协议，减少不同客户端重复适配同一工具的成本。

MCP 基本结构：

```text
MCP Client
  -> MCP Protocol
    -> MCP Server
      -> Tool
      -> Resource
      -> Prompt
```

MCP 三大原语：

- **Tool**：可执行动作，例如查询数据库、创建 Issue、运行搜索、调用业务 API。
- **Resource**：可读取资源，例如文件、日志、文档、数据库记录、网页内容。
- **Prompt**：可复用提示模板，例如代码审查模板、SQL 分析模板、日报生成模板。

MCP Server 的工程价值：

- 将外部能力包装为结构化接口。
- 通过 schema 限制工具参数，降低误调用概率。
- 将模型与具体系统解耦，便于跨客户端复用。
- 允许对高风险操作增加权限检查和人工确认。

示例配置：

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "./docs"]
    }
  }
}
```

Skill 用于封装高频、细粒度、可复用的操作能力。与 MCP 侧重“连接外部能力”不同，Skill 侧重“固化任务方法”。一个代码审查 Skill 通常包含审查优先级、命令清单、输出格式、项目约束和参考资料。

Skill 的典型内容：

- 任务触发条件。
- 标准操作步骤。
- 可复用脚本或模板。
- 输出格式约束。
- 领域知识和注意事项。

MCP 与 Skill 的关系：

```text
MCP = 工具接入层，解决“能调用什么”
Skill = 方法封装层，解决“应该怎样做”
```

### 3. Vibe Coding 范式导论

Vibe Coding 的核心不是随机对话式生成代码，而是用自然语言编排可执行的工程意图。高质量意图描述必须具备结构化信息，使模型能够正确定位任务、控制范围并输出可验证结果。

自然语言编排应覆盖六类信息：

1. **目标**
   明确要完成的用户价值或工程结果，避免只描述技术动作。

2. **输入输出**
   定义用户输入、系统输出、数据结构、异常路径和边界条件。

3. **关联模块**
   指明相关文件、函数、接口、路由、数据库表、配置项和调用链。

4. **约束条件**
   说明禁止修改的文件、必须沿用的风格、性能要求、安全要求和兼容性要求。

5. **验收标准**
   明确通过哪些测试、构建命令、页面行为、接口响应或人工检查才算完成。

6. **交付格式**
   指定需要代码、测试、文档、迁移脚本、评估报告还是设计说明。

推荐任务描述模板：

```text
背景：
  项目类型、技术栈、相关目录、当前问题。

目标：
  本次变更要达成的业务结果或工程结果。

输入输出：
  输入来源、输出结构、异常处理、边界情况。

关联模块：
  涉及文件、接口、函数、数据库表、配置项。

约束：
  不能修改的内容、必须保持的兼容性、性能和安全要求。

验收：
  必须通过的命令、测试、页面行为、日志检查或人工验证项。
```

低质量任务描述：

```text
帮我做一个 AI 笔记系统。
```

高质量任务描述：

```text
背景：
  现有项目是 MkDocs Material 知识库，文档目录为 docs/。

目标：
  新增一篇 Vibe Coding 与 Agent 学习路线笔记，文件名为 docs/vibecoding.md。

约束：
  使用标准 Markdown 标题；必须包含名词对比表；不得修改其他笔记内容。

验收：
  mkdocs build --strict 可以通过；表格渲染正常；标题层级符合 MkDocs TOC。
```

### 4. 提示词工程

提示词工程的目标是降低需求歧义、控制模型输出范围、提升可验证性。高质量提示词不追求花哨表达，而追求上下文充分、目标明确、约束可执行、验收可检查。

四大核心要素：

| 要素 | 作用 | 关键问题 |
| --- | --- | --- |
| 背景 | 提供项目上下文和任务环境 | 当前系统是什么，已有约定是什么 |
| 目标 | 定义本次任务的完成状态 | 要解决什么问题，用户价值是什么 |
| 约束 | 限定修改范围和风险边界 | 不能改什么，必须遵循什么 |
| 验收 | 建立客观完成标准 | 运行什么命令，检查什么行为 |

提示词中的约束应尽量可执行：

- “保持代码整洁”属于弱约束。
- “沿用现有 `services/` 分层，不新增全局状态；新增逻辑必须有单元测试”属于强约束。

提示词中的验收应尽量可验证：

- “功能正常”属于弱验收。
- “`npm test`、`npm run build` 通过；登录失败时返回 401；空密码返回表单校验错误”属于强验收。

面向代码修改的提示词示例：

```text
背景：
  当前项目使用 FastAPI + SQLAlchemy。用户登录逻辑位于 app/auth/。

目标：
  为登录接口增加账号锁定机制。连续 5 次密码错误后锁定 15 分钟。

约束：
  不改变现有登录响应字段；不引入新数据库；沿用现有 User 模型迁移方式。

验收：
  新增单元测试覆盖：失败次数累计、锁定期间拒绝登录、锁定过期后允许登录。
  pytest 必须通过。
```

提示词常见错误：

- 只给目标，不给上下文。
- 只给功能，不给边界条件。
- 只要求“优化”，不定义指标。
- 一次要求实现、重构、换框架、补测试、写文档，导致任务范围失控。
- 缺少验收命令，模型无法形成闭环。

### 5. 最小可行产品

MVP（Minimum Viable Product）是用最小实现验证核心假设的工程策略。AI 辅助开发场景中，MVP 的意义更加重要：模型生成速度很快，如果没有范围控制，系统会快速堆积不可验证的复杂度。

MVP 构建原则：

- **单一主路径**：先实现最关键用户流程。
- **最小依赖**：优先使用现有技术栈和轻量存储。
- **可运行优先**：先跑通端到端流程，再完善异常和扩展能力。
- **可观测优先**：关键路径必须有日志、错误信息或测试反馈。
- **可删除优先**：原型代码应便于替换，避免过早绑定复杂架构。

示例：AI 文档摘要工具的 MVP 范围。

必须实现：

1. 输入一段文档文本。
2. 调用模型生成摘要。
3. 输出固定结构：核心问题、关键方法、主要结论。
4. 保存一次运行结果。
5. 提供最小测试或手动验收脚本。

暂缓实现：

- 多用户系统。
- 复杂权限模型。
- 向量数据库。
- 自动爬取外部文档。
- 精细化前端交互。

AI 代码审核规范：

- **API 真实性**：核对官方文档、本地类型定义或依赖源码。
- **依赖一致性**：检查 `package.json`、`requirements.txt`、`pyproject.toml`、锁文件。
- **调用链完整性**：确认新增函数被真实调用，删除代码无残留引用。
- **错误路径覆盖**：检查空输入、超时、权限不足、网络失败、并发冲突。
- **安全边界**：排查密钥泄露、命令注入、SQL 注入、路径穿越、越权访问。
- **测试有效性**：测试必须断言真实行为，避免只检查函数被调用或快照存在。

AI 幻觉识别清单：

- 生成了项目中不存在的文件路径。
- 使用了依赖中不存在的函数、参数或配置字段。
- 忽略已有架构，重新发明一套并行抽象。
- 给出无法复现的报错解释。
- 测试用例只适配生成代码，而不验证真实需求。
- 文档描述与代码行为不一致。

### 6. 迭代式开发循环

稳定的 Vibe Coding 应采用“描述 -> 生成 -> 运行 -> 反馈 -> 修改”的闭环，而不是一次性生成大段代码。

标准循环：

1. **描述**
   明确背景、目标、约束、验收。

2. **生成**
   生成最小可审查 diff，避免无关重构。

3. **运行**
   执行格式化、静态检查、单元测试、集成测试、构建或启动验证。

4. **反馈**
   将真实错误日志、失败测试、截图、diff 和运行环境返回给模型。

5. **修改**
   基于证据修复问题，避免基于猜测扩大改动范围。

6. **沉淀**
   将重复流程固化为脚本、Hook、CI、Skill 或文档。

典型命令链：

```bash
npm run format
npm run lint
npm test
npm run build
```

MkDocs 项目验收命令：

```bash
mkdocs build --strict
```

Hooks 用于把高频检查自动化，降低人为遗漏。常见 Hook 类型：

- **格式化 Hook**：Prettier、Black、Ruff format、go fmt。
- **静态检查 Hook**：ESLint、Ruff、mypy、tsc。
- **测试 Hook**：pytest、vitest、go test。
- **构建 Hook**：Vite build、MkDocs build、Docker build。
- **提交规范 Hook**：commitlint、secret scan、YAML/JSON 校验。

`pre-commit` 示例：

```yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-json
      - id: detect-private-key
```

长上下文管理的工程演进路径：

1. **文件级上下文**
   适合小修改。只提供当前文件、相关测试和错误日志。

2. **模块级上下文**
   适合跨文件功能。提供接口定义、调用链、数据模型和测试入口。

3. **项目级规则**
   适合长期维护。使用 `README`、`CONTRIBUTING`、架构文档、ADR 记录稳定约束。

4. **RAG**
   适合大规模文档和代码知识库。通过检索相关片段降低上下文窗口压力。

5. **SubAgent**
   适合并行分析、审查、测试、研究。通过角色隔离减少上下文污染。

6. **Agent Team**
   适合复杂工程任务。通过 Planner、Coder、Reviewer、Researcher、QA、Writer 等角色协作形成多步骤闭环。

RAG（Retrieval-Augmented Generation）流程：

```text
文档切分 -> 向量化 -> 相似度检索 -> 重排序 -> 上下文注入 -> 基于证据生成
```

RAG 核心痛点：

- chunk 粒度影响召回和噪声。
- embedding 相似度不等于任务相关性。
- 检索结果需要重排序和去重。
- 生成阶段必须约束模型基于证据回答。
- 知识库更新后索引必须同步刷新。

SubAgent 与 Agent Team 的引入条件：

- 任务可并行拆分。
- 子任务边界明确。
- 需要上下文隔离。
- 需要多视角审查。
- 汇总成本低于并行收益。

典型 Agent Team：

```text
Planner Agent：拆解任务、定义依赖关系和验收路线
Coder Agent：实现代码和局部测试
Reviewer Agent：审查正确性、安全性和回归风险
Research Agent：核对官方文档和版本差异
QA Agent：运行测试、复现用户路径、整理失败证据
Writer Agent：生成文档、变更说明和使用示例
```

## 名词概念速通

| 名词 | 技术本质/定义 | 一句话通俗理解 | 在 Vibe Coding 中的角色 |
| --- | --- | --- | --- |
| LLM | 基于大规模语料训练的生成模型，通过上下文预测 token，并经过指令微调具备问答、代码生成和推理能力。 | 能根据上下文生成高概率文本和代码的通用生成引擎。 | 负责代码生成、错误解释、方案草拟、测试补全和文档生成。 |
| Function Calling | 模型输出结构化函数名和参数，由外部程序执行真实函数并返回结果。 | 让模型从“说答案”升级为“调用工具办事”。 | 将自然语言意图转化为 API 调用、数据库查询、文件操作或脚本执行。 |
| Agent | 带目标、状态、工具、记忆和反馈循环的任务执行系统。 | 能围绕目标连续行动的 LLM 应用。 | 串联需求分析、代码修改、测试运行、错误修复和结果汇报。 |
| SubAgent | 为特定子任务隔离上下文、职责和工具权限的子智能体。 | 专门处理一个局部任务的隔离执行单元。 | 用于并行研究、代码审查、测试验证、文档生成和复杂任务拆解。 |
| MCP | Model Context Protocol，标准化模型应用连接外部工具、资源和提示模板的协议。 | AI 应用连接外部世界的统一插座。 | 让不同 AI 客户端复用文件系统、数据库、搜索、知识库等能力。 |
| Tool | MCP 原语之一，表示模型可触发的可执行动作。 | 可以被模型调用的函数或操作。 | 执行搜索、读写文件、创建任务、查询数据库、运行业务 API。 |
| Resource | MCP 原语之一，表示模型可读取的上下文资源。 | 提供给模型参考的外部材料。 | 注入项目文件、日志、文档、数据库记录、网页内容。 |
| Prompt | MCP 原语之一，表示可复用的提示模板。 | 固化任务格式和操作套路的模板。 | 统一代码审查、SQL 分析、文档生成、调试流程的输入结构。 |
| MCP Server | 暴露 Tool、Resource、Prompt 的服务端组件，供 MCP Client 连接和调用。 | 把外部系统包装成模型可理解接口的适配层。 | 将文件系统、GitHub、数据库、浏览器、企业系统接入 Agent。 |
| Workflow | 将任务拆成节点、状态、条件分支、工具调用和停止条件的流程结构。 | 给 Agent 规定可观察、可回退、可调试的执行路线。 | 约束模型行为，避免无限循环和无边界自由生成。 |
| Langchain | 面向 LLM 应用的组件框架，提供模型调用、Prompt、工具、检索、链式组合等抽象。 | LLM 应用开发的工具箱。 | 快速搭建 RAG、工具调用、文档问答和原型 Agent。 |
| LangGraph | 基于图结构和状态机思想的 Agent 工作流框架，适合循环、分支、多 Agent 和人工介入。 | 用图来描述 Agent 的状态流转。 | 构建可控的多步骤 Agent、复杂 Workflow 和多代理协同系统。 |
| Skill | 将高频任务的流程、脚本、模板和领域知识封装为可复用能力。 | 给 Agent 的专项操作手册。 | 固化代码审查、测试修复、文档生成、部署检查等高频动作。 |
| 可视化编排 | 通过图形界面配置节点、条件、工具和数据流的工作流搭建方式。 | 用拖拽节点搭 Agent 流程。 | 适合业务原型、非复杂状态流程和快速验证，但复杂逻辑需要代码化治理。 |

## DataWhale: hello-agent 路线

### 1. 基础主线

DataWhale `hello-agents` 路线围绕“从零开始构建智能体”展开，适合从基础概念过渡到工程实现。

智能体发展史可按技术范式划分：

1. **符号主义与专家系统**
   依赖人工规则、知识库和推理引擎，优点是可解释，缺点是知识获取成本高、泛化能力弱。

2. **机器学习与强化学习智能体**
   通过数据或环境反馈学习策略，适合明确奖励函数场景，但在开放文本任务和通用工具使用上受限。

3. **LLM 驱动的工具型 Agent**
   借助语言模型理解任务、生成计划，并通过 Function Calling 或 Tool Use 调用外部工具。

4. **多 Agent 与社会模拟**
   多个 Agent 通过通信、分工、协作和环境反馈完成复杂任务或模拟群体行为。

大模型基础应覆盖：

- token 与上下文窗口。
- temperature、top-p 等解码参数。
- embedding 与语义检索。
- 指令微调与对齐。
- 函数调用与工具使用。
- 上下文压缩与长程依赖问题。

经典 Agent 范式：

- **ReAct**：Reasoning 与 Acting 交替执行，通过“思考 -> 行动 -> 观察”形成反馈循环。
- **Plan-and-Execute**：先生成计划，再逐步执行，适合长任务。
- **Reflection**：执行后自评和修正，适合复杂推理和代码修复。
- **Tool Use**：根据任务动态选择工具，将模型输出落到真实环境。
- **Multi-Agent Debate**：多个 Agent 从不同角度讨论或审查，降低单点偏差。

### 2. 框架与实践

主流 Agent 框架通常提供以下能力：

- 模型调用适配。
- Prompt 模板管理。
- Tool schema 定义。
- Memory 与 Retrieval。
- Agent Loop。
- Workflow 状态管理。
- 多 Agent 通信。
- Trace、日志和评估。

常见框架定位：

| 框架 | 定位 | 适用场景 |
| --- | --- | --- |
| LangChain | LLM 应用组件库 | RAG、工具调用、文档问答、快速原型 |
| LangGraph | 状态图与 Agent Workflow | 多步骤任务、循环、分支、多 Agent、人工审批 |
| LlamaIndex | 数据连接与检索增强 | 文档索引、知识库问答、企业数据检索 |
| AutoGen | 多 Agent 对话与协作 | 多角色协作、研究原型、任务分解 |
| CrewAI | 角色化 Agent Team | 业务流程、多角色任务执行 |
| Dify / Coze | 低代码 Agent 平台 | 快速搭建应用、工作流原型、知识库问答 |

低代码搭建边界：

- 适合验证流程，不适合承载复杂状态机。
- 适合固定业务链路，不适合强定制调度逻辑。
- 适合快速演示，不适合缺少测试、版本控制和权限治理的生产系统。
- 当节点数量快速膨胀、数据结构频繁变化、错误难以复现时，应转向代码化框架。

自主构建 Agent 框架的最小结构：

```text
agent/
  llm_client.py      # 模型调用
  tool_registry.py   # 工具注册和 schema
  prompt_builder.py  # 上下文与提示词组装
  memory_store.py    # 短期/长期记忆
  loop.py            # plan-act-observe-update-stop
  tracing.py         # 调用链记录与调试
  eval.py            # 任务评估
```

Agent Loop 伪代码：

```python
while not done:
    prompt = build_prompt(state, tools, memory)
    decision = llm.generate(prompt)
    action = parse_action(decision)
    observation = execute_tool(action)
    state = update_state(state, action, observation)
    done = should_stop(state)
```

智能体性能评估（Evaluation）用于判断系统是否真的变强，而不是只在单次演示中表现良好。

核心评估维度：

| 维度 | 指标 | 说明 |
| --- | --- | --- |
| 任务成功率 | success rate、人工评分 | 最终目标是否完成 |
| 工具调用质量 | tool accuracy、invalid calls | 工具选择和参数是否正确 |
| 过程效率 | latency、token cost、step count | 时间、成本和步骤数是否可接受 |
| 稳定性 | pass@k、结果方差 | 多次运行是否一致 |
| 安全性 | policy violation、blocked actions | 是否越权、泄露或误操作 |
| 可解释性 | trace completeness | 是否能复盘每一步决策 |

评估集应包含正常任务、边界任务、对抗输入、工具失败、信息不足和需要人工确认的任务。没有固定评估集的 Agent 只能算 Demo，不能证明能力提升。

### 3. 记忆、检索与上下文

Memory & Retrieval 是 Agent 从单轮问答走向长期任务执行的关键组件。

记忆类型：

- **短期记忆**：当前对话、当前任务状态、最近工具观察。
- **长期记忆**：用户偏好、项目规范、历史决策、稳定事实。
- **情景记忆**：特定事件的时间、地点、参与者和结果。
- **语义记忆**：可检索的知识片段，如文档、代码、笔记。
- **程序性记忆**：固定操作流程，可沉淀为 Skill 或 Workflow。

记忆系统的关键难点：

- 写入什么：不是所有对话都值得进入长期记忆。
- 何时检索：检索触发条件需要与任务意图绑定。
- 检索多少：过少导致信息缺失，过多导致噪声污染。
- 如何排序：需要基于相关性、新鲜度、可信度和任务阶段综合排序。
- 如何遗忘：过期偏好、错误事实和临时状态必须可清理。

Retrieval 典型流水线：

```text
query rewrite
  -> hybrid search
  -> rerank
  -> deduplicate
  -> filter stale context
  -> inject evidence
  -> grounded generation
```

Context Engineering 是比“扩大上下文窗口”更重要的工程能力。上下文不是越多越好，而是需要让模型在每一步看到最小充分信息。

上下文应包含：

- 当前目标。
- 当前状态。
- 相关代码或文档。
- 可用工具及参数 schema。
- 禁止行为。
- 最近观察结果。
- 验收标准。

上下文应避免：

- 无关历史对话。
- 重复或过期文档。
- 未验证猜测。
- 大量无关代码。
- 敏感信息。

有效上下文设计原则：

- **结构化**：用明确字段组织目标、事实、约束和观察。
- **可追溯**：检索内容带来源，便于核查。
- **可压缩**：长任务阶段性总结，保留决策和状态。
- **可更新**：工具结果、测试反馈和用户变更及时覆盖旧信息。
- **最小充分**：只注入完成当前步骤所需上下文。

### 4. 工具、协议与协作

工具调用使 Agent 从文本生成系统变成可执行系统。协议和协作机制决定多 Agent 系统是否可控。

工具设计原则：

- 参数必须有 schema。
- 返回值必须结构化。
- 错误必须显式表达。
- 高风险动作需要人工确认。
- 工具权限遵循最小权限原则。
- 工具调用过程必须记录 trace。

多 Agent 通信协议应避免纯自然语言自由传递，推荐使用结构化消息。

示例：

```json
{
  "sender": "reviewer",
  "receiver": "coder",
  "task_id": "auth-lockout",
  "message_type": "review_findings",
  "severity": "high",
  "findings": [
    {
      "file": "app/auth/service.py",
      "issue": "failed login counter is not reset after successful login",
      "expected_fix": "reset counter and add regression test"
    }
  ]
}
```

多 Agent 协作机制：

- **角色分工**：Planner、Coder、Reviewer、Researcher、QA、Writer。
- **上下文隔离**：每个 Agent 只读取必要信息。
- **消息协议**：使用结构化字段传递任务、证据、状态和请求。
- **冲突解决**：由主 Agent 或人类决策者合并冲突结论。
- **统一评估**：所有 Agent 输出进入同一验收链路。

智能旅行助手系统架构：

```text
User Request
  -> Preference Parser
  -> Planner Agent
  -> Tool Layer
       -> Search API
       -> Map API
       -> Weather API
       -> Calendar API
       -> Budget Calculator
  -> Constraint Checker
  -> Itinerary Generator
  -> User Feedback Loop
```

关键工程点：

- 外部信息强时效性，需要实时检索。
- 用户偏好可能冲突，需要约束求解。
- 工具结果格式不统一，需要规范化中间表示。
- 输出必须可执行，而不是只生成流畅文案。

赛博小镇（Generative Agents）系统架构：

```text
Environment
  -> Observation
  -> Memory Write
  -> Memory Retrieval
  -> Reflection
  -> Planning
  -> Action
  -> Environment Update
  -> Other Agents Observe
```

核心模块：

- **环境状态**：地点、时间、事件、对象。
- **角色状态**：身份、目标、关系、计划。
- **记忆系统**：事件写入、重要性评分、检索。
- **反思机制**：从多条记忆抽象出高层信念。
- **计划器**：生成日程和局部行动。
- **交互协议**：Agent 与环境、Agent 与 Agent 的通信格式。

Generative Agents 的难点包括状态爆炸、记忆污染、成本控制、行为一致性和可解释性。

## 推荐学习顺序

1. **Vibe Coding 实用工程路线**

   适合目标是快速提升开发交付效率的学习者。

   1. LLM 基础：token、上下文、幻觉、解码参数。
   2. 工具链：Cursor、Windsurf、CLI Agent、Git、测试框架。
   3. 提示词工程：背景、目标、约束、验收。
   4. MVP：最小用户路径、最小依赖、最小测试。
   5. 自动化闭环：格式化、静态检查、测试、构建、Hook。
   6. RAG：为项目文档、知识库和代码上下文提供检索能力。
   7. Agent Team：将生成、审查、研究、测试和文档拆成独立角色。

2. **Agent 系统理论研究路线**

   适合目标是理解底层协议、框架演进和多代理协同的学习者。

   1. LLM：生成机制、上下文窗口、embedding、对齐。
   2. Function Calling：工具 schema、结构化参数、调用结果回传。
   3. Agent Loop：plan、act、observe、update、stop。
   4. MCP：Tool、Resource、Prompt、MCP Server。
   5. Workflow：ReAct、Plan-and-Execute、Reflection、Human-in-the-loop。
   6. 框架：LangChain、LangGraph、LlamaIndex、AutoGen、CrewAI。
   7. Memory & Retrieval：长期记忆、RAG、上下文压缩、证据引用。
   8. Multi-Agent：通信协议、角色分工、冲突解决、协同评估。

## 最后记法

Vibe Coding 与 Agent 工程可以用一个职责闭环记忆：

```text
人定义目标与验收
  -> 模型生成候选方案
  -> 工具连接真实环境
  -> Agent 串联多步骤执行
  -> 上下文工程控制信息流
  -> 自动化测试与评估提供反馈
  -> 人做最终取舍
```

各组件职责：

- **人**：定义问题、设置边界、审查风险、决定取舍。
- **模型**：生成代码、解释错误、提出方案、补全文档。
- **工具**：执行命令、读写文件、查询系统、调用 API。
- **Agent**：维护状态、选择工具、组织步骤、处理反馈。
- **上下文工程**：选择信息、压缩历史、注入证据、避免污染。
- **评估系统**：度量成功率、成本、稳定性、安全性和可解释性。

最终目标不是让 AI “自由写代码”，而是构建一个可验证、可回滚、可复盘、可扩展的 AI 辅助工程系统。
