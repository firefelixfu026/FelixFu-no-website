# 计算机网络基础

## 1. TCP/IP 网络分层模型

**模型概述**：TCP/IP 网络分层模型用于把复杂的网络通信拆解为多个职责清晰的层级。每一层只关注本层需要解决的问题，并向上层提供稳定服务。分层的意义在于降低系统复杂度：应用程序不需要直接处理电信号，网络设备也不需要理解网页、邮件或文件传输的业务语义。

经典 TCP/IP 模型通常划分为四层：

- 应用层
- 传输层
- 网络层
- 网络接口层

在工程学习中，网络接口层经常进一步拆成**数据链路层**和**物理层**，形成更直观的五层理解方式。五层模型便于从“应用数据”一路追踪到“物理信号”，也更适合分析浏览器访问网页、服务器通信、局域网转发等实际场景。

数据在网络中传输时，会经历逐层封装与逐层解封装：

```text
应用数据
  -> 传输层封装端口信息，形成 TCP/UDP 段
  -> 网络层封装 IP 地址，形成 IP 数据包
  -> 数据链路层封装 MAC 地址，形成帧
  -> 物理层转换为 0/1 信号在介质上传输
```

**各层核心职责逐层拆解**：

- **应用层 (Application Layer)**

  应用层负责处理应用程序之间的通信规则，规定数据的语义、格式和交互流程。常见协议包括 HTTP、HTTPS、FTP、SMTP、DNS 等。

  典型职责：

  - 定义请求和响应的数据格式。
  - 规定客户端与服务器之间的交互方式。
  - 面向具体业务场景，例如网页访问、文件传输、邮件发送、域名解析。

- **传输层 (Transport Layer)**

  传输层负责端到端的数据传输，即从一台主机上的某个进程传输到另一台主机上的某个进程。传输层引入**端口号**，用于区分同一台设备上的不同网络进程，端口范围为 `0-65535`。

  核心协议：

  - **TCP**：面向连接，提供可靠传输、顺序保证、流量控制和拥塞控制。
  - **UDP**：无连接，开销小，延迟低，不保证可靠性和顺序。

  典型理解：

  ```text
  IP 地址定位主机
  端口号定位主机上的具体进程
  ```

- **网络层 (Network Layer)**

  网络层负责数据包在不同网络之间的路由与转发。它解决的是“数据包应该从哪条路径到达目标网络”的问题。IP 地址是网络层的核心标识，用于在网络范围内定位设备。

  网络层还涉及 IP 地址与物理 MAC 地址之间的映射。在 IPv4 局域网中，ARP 协议常用于根据目标 IP 地址解析对应的 MAC 地址，从而让数据链路层完成实际帧转发。

- **数据链路层 (Link Layer)**

  数据链路层负责在同一物理网络或同一链路范围内传输数据。它将网络层传下来的 IP 数据包封装为**帧 (Frame)**，并使用 MAC 地址标识链路层上的发送方与接收方。

  典型职责：

  - 定义帧格式。
  - 使用 MAC 地址完成局域网内转发。
  - 进行错误检测，例如以太网帧中的 FCS 校验。
  - 在部分链路协议中提供错误校正或重传机制。

- **物理层 (Physical Layer)**

  物理层负责最底层的 0/1 信号传输。它不关心 IP、端口、HTTP 等逻辑概念，只负责通过网线、光纤、无线电波等介质传递比特流。

  典型内容包括：

  - 电压、电磁波、光信号等物理信号形式。
  - 网线、光纤、无线信道等传输介质。
  - 比特率、编码方式、物理接口标准。

## 2. 网络层与传输层核心要素

### 2.1 IP地址、子网掩码与路由

**IP 地址**：IP 地址用于在网络层唯一标识网络设备或网络接口。常见版本包括 IPv4 和 IPv6。

- **IPv4**：长度为 32 位，通常写作点分十进制，例如 `192.168.1.10`。IPv4 地址数量有限，因此现实网络中大量使用 NAT、私有地址和子网划分。
- **IPv6**：长度为 128 位，通常写作冒号分隔的十六进制，例如 `2001:db8::1`。IPv6 设计目标之一是提供更大的地址空间。

IPv4 地址一般由两部分组成：

```text
网络地址 + 主机地址
```

网络地址用于标识设备所在的网络，主机地址用于标识该网络中的具体设备。

**子网掩码**：子网掩码用于区分 IP 地址中的网络位和主机位。子网掩码中为 `1` 的部分表示网络位，为 `0` 的部分表示主机位。

示例：

```text
IP 地址：   192.168.1.10
子网掩码： 255.255.255.0

网络地址： 192.168.1.0
主机范围： 192.168.1.1 - 192.168.1.254
广播地址： 192.168.1.255
```

也可以使用 CIDR 形式表示：

```text
192.168.1.10/24
```

其中 `/24` 表示前 24 位是网络位，剩余 8 位是主机位。

子网掩码的主要价值：

- 划分更小的网络范围。
- 控制广播域大小。
- 提高 IP 地址规划的灵活性。
- 帮助主机判断目标 IP 是否在同一网络内。

**路由**：路由是数据包跨越不同网络进行传输的转发机制。当目标 IP 不在本地网络内时，主机会把数据包交给默认网关，由路由器根据路由表逐跳转发，直到到达目标网络。

路由过程的核心问题是：

```text
目标 IP 属于哪个网络？
下一跳设备是谁？
应该从哪个网络接口发出？
```

路由表通常包含：

- 目标网络。
- 子网掩码或前缀长度。
- 下一跳地址。
- 出口网络接口。
- 路由优先级或度量值。

### 2.2 DNS 与域名解析

**DNS 的作用**：DNS（Domain Name System，域名系统）用于将人类可读的域名转换为计算机可定位的 IP 地址。用户更容易记住 `www.example.com`，但计算机通信最终需要使用 IP 地址定位目标主机。

DNS 的核心价值：

- 用域名屏蔽底层 IP 地址变化。
- 通过层级结构管理全球域名。
- 支持负载均衡、故障切换和地理位置调度。
- 降低用户记忆成本，提高服务迁移灵活性。

**解析流程梳理**：

1. **浏览器接收域名**

   用户在浏览器输入 URL，例如：

   ```text
   https://www.example.com/index.html
   ```

   浏览器首先提取主机名 `www.example.com`，后续需要将其解析为 IP 地址。

2. **查询浏览器 DNS 缓存**

   浏览器会优先检查自身缓存。如果缓存中存在未过期的解析结果，则直接使用该 IP 地址。

3. **查询操作系统 DNS 缓存**

   如果浏览器缓存未命中，操作系统会检查本地 DNS 缓存，常见系统会缓存近期解析过的域名结果。

4. **检查本地 hosts 文件**

   操作系统可能会读取 hosts 文件。hosts 文件提供静态域名到 IP 的映射，优先级通常高于外部 DNS 查询。

5. **向本地 DNS 服务器发起请求**

   如果本地仍未命中，系统会向配置的本地 DNS 服务器发起查询。本地 DNS 服务器通常由路由器、运营商或公共 DNS 服务提供。

6. **递归或迭代查询权威 DNS**

   本地 DNS 服务器如果没有缓存，会继续查询根域名服务器、顶级域名服务器和权威域名服务器，逐步定位最终记录。

7. **返回解析结果**

   DNS 服务器将 IP 地址返回给操作系统，操作系统再交给浏览器。

8. **建立连接并缓存结果**

   浏览器使用解析得到的 IP 地址建立 TCP 或 TLS 连接，并按 DNS 记录的 TTL 缓存解析结果。

## 3. HTTP 协议详解

### 3.1 协议概述

HTTP（HyperText Transfer Protocol，超文本传输协议）是 Web 中最核心的应用层协议之一。它采用经典的**请求-响应**模型：客户端发送请求，服务器处理请求并返回响应。

典型流程：

```text
客户端浏览器
  -> 发送 HTTP 请求
  -> Web 服务器处理请求
  -> 返回 HTTP 响应
  -> 浏览器解析并渲染结果
```

前后端必须基于统一通信协议进行数据交互，原因在于：

- **请求格式统一**：前端知道如何表达资源路径、请求方法、请求头和请求体。
- **响应格式统一**：后端按约定返回状态码、响应头和响应体。
- **语义明确**：GET、POST、PUT、DELETE 等方法表达不同操作意图。
- **跨语言协作**：前端可以使用 JavaScript，后端可以使用 Java、Python、Go、Node.js，只要遵循 HTTP 规范即可通信。
- **基础设施兼容**：浏览器、代理、网关、CDN、负载均衡器都能识别 HTTP。

HTTP 本身是无状态协议。服务器默认不会记住两次请求之间的关系，因此 Web 应用通常借助 Cookie、Session、Token 等机制维护登录状态和用户上下文。

### 3.2 HTTP 请求与响应结构

**请求结构**：HTTP 请求由请求行、请求头、空行和请求体组成。

```text
GET /users?id=1 HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Accept: application/json

```

主要组成部分：

- **请求方法**

  请求方法用于表达客户端希望对资源执行的操作。

  | 方法 | 主要用途 | 常见场景 |
  | --- | --- | --- |
  | GET | 获取资源 | 打开页面、查询列表、获取详情。 |
  | POST | 提交数据或创建资源 | 登录、注册、提交表单、创建订单。 |
  | PUT | 整体更新资源 | 替换用户资料、更新完整配置。 |
  | PATCH | 局部更新资源 | 修改昵称、更新部分字段。 |
  | DELETE | 删除资源 | 删除文章、移除记录。 |

- **请求 URL**

  URL 用于定位资源，通常包含协议、主机名、端口、路径和查询参数。

  ```text
  https://api.example.com:443/users?id=1
  ```

  拆解如下：

  - `https`：协议。
  - `api.example.com`：主机名。
  - `443`：端口号。
  - `/users`：资源路径。
  - `id=1`：查询参数。

- **请求头 (Headers)**

  请求头用于携带请求的元数据，例如客户端类型、内容格式、身份凭证、缓存策略。

  常见请求头：

  | 请求头 | 作用 |
  | --- | --- |
  | Host | 指定目标主机名。 |
  | User-Agent | 描述客户端类型和版本。 |
  | Accept | 声明客户端可接收的响应类型。 |
  | Content-Type | 声明请求体的数据格式。 |
  | Authorization | 携带身份认证信息，例如 Bearer Token。 |
  | Cookie | 携带浏览器保存的站点状态。 |

- **请求体 (Body)**

  请求体用于承载提交给服务器的数据。GET 请求通常没有请求体，POST、PUT、PATCH 常携带请求体。

  JSON 请求体示例：

  ```json
  {
    "username": "alice",
    "password": "example-password"
  }
  ```

**响应结构**：HTTP 响应由状态行、响应头、空行和响应体组成。

```text
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-cache

{"id":1,"name":"alice"}
```

主要组成部分：

- **状态码**

  状态码用于说明服务器对请求的处理结果。它让客户端能够快速判断请求成功、重定向、认证失败、资源不存在或服务器异常。

- **响应头 (Headers)**

  响应头用于描述响应元数据，例如内容类型、缓存策略、服务器信息、Cookie 设置、跨域策略。

  常见响应头：

  | 响应头 | 作用 |
  | --- | --- |
  | Content-Type | 声明响应体格式，例如 `text/html`、`application/json`。 |
  | Content-Length | 声明响应体长度。 |
  | Cache-Control | 控制缓存策略。 |
  | Set-Cookie | 要求浏览器保存 Cookie。 |
  | Location | 配合重定向状态码，指示新的访问地址。 |
  | Access-Control-Allow-Origin | 控制跨域资源访问。 |

- **响应体 (Body)**

  响应体是服务器返回的实际内容，可以是 HTML 页面、JSON 数据、图片、文件流或错误信息。

**核心状态码速查**：

| 状态码 | 状态简述 | 典型应用场景/触发原因 |
| --- | --- | --- |
| 200 | OK，请求成功 | 页面加载成功、接口成功返回数据、文件正常下载。 |
| 201 | Created，资源已创建 | POST 创建用户、订单、文章等资源成功。 |
| 204 | No Content，无响应体 | 删除成功或更新成功，但服务器不需要返回内容。 |
| 301 | Moved Permanently，永久重定向 | 旧域名迁移到新域名，HTTP 跳转到 HTTPS。 |
| 302 | Found，临时重定向 | 登录后跳转、临时活动页跳转、短链接跳转。 |
| 304 | Not Modified，资源未修改 | 浏览器缓存验证命中，服务器通知客户端继续使用缓存。 |
| 400 | Bad Request，请求格式错误 | 参数类型错误、JSON 格式错误、缺少必要字段。 |
| 401 | Unauthorized，未认证 | 未登录、Token 缺失、Token 过期或认证信息无效。 |
| 403 | Forbidden，禁止访问 | 已认证但权限不足，例如普通用户访问管理员接口。 |
| 404 | Not Found，资源不存在 | URL 路径错误、资源 ID 不存在、静态文件缺失。 |
| 405 | Method Not Allowed，方法不允许 | 对只支持 GET 的接口发送 POST 请求。 |
| 500 | Internal Server Error，服务器内部错误 | 代码异常、数据库错误、未捕获异常、服务端逻辑崩溃。 |
| 502 | Bad Gateway，网关错误 | 反向代理无法从上游服务获得有效响应。 |
| 503 | Service Unavailable，服务不可用 | 服务维护、过载、限流或临时不可用。 |

## 4. HTTPS 安全加密机制

**协议本质**：HTTPS（HyperText Transfer Protocol Secure）是 HTTP 的安全版本。它并不是一个全新的应用层协议，而是在 HTTP 与传输层之间引入 TLS/SSL 安全层，使原本明文传输的 HTTP 数据具备加密、认证和完整性保护能力。

HTTP 与 HTTPS 的核心区别：

| 对比项 | HTTP | HTTPS |
| --- | --- | --- |
| 默认端口 | 80 | 443 |
| 数据传输 | 明文 | 加密 |
| 身份验证 | 无内建服务器身份验证 | 通过数字证书验证服务器身份 |
| 数据完整性 | 容易被中间人篡改且难以发现 | 通过完整性校验发现篡改 |
| 典型风险 | 窃听、篡改、冒充 | 主要风险转移到证书信任链、私钥保护和协议配置 |

**三大核心安全支柱拆解**：

1. **数据加密传输**

   HTTPS 通过 TLS 协议协商会话密钥，并使用对称加密算法加密后续通信数据。对称加密速度快，适合大量应用数据传输；非对称加密或密钥交换机制则用于安全协商会话密钥。

   简化流程：

   ```text
   客户端发起 TLS 握手
     -> 服务器返回证书和密钥交换参数
     -> 客户端验证证书
     -> 双方协商会话密钥
     -> 后续 HTTP 数据使用会话密钥加密传输
   ```

   加密传输的作用是防止中间人直接读取账号、密码、Cookie、Token、请求参数等敏感信息。

2. **身份验证机制**

   HTTPS 使用数字证书证明服务器身份。服务器证书通常由 CA（Certificate Authority，证书颁发机构）签发，证书中包含域名、公钥、有效期、签发者和数字签名等信息。

   客户端验证证书时会检查：

   - 证书是否由受信任 CA 签发。
   - 证书绑定的域名是否与访问域名匹配。
   - 证书是否在有效期内。
   - 证书是否被吊销。
   - 证书签名是否有效。

   该机制可以降低恶意服务器伪装成目标网站的风险。如果缺少身份验证，攻击者即使无法破解加密算法，也可能通过中间人攻击诱导客户端连接到伪造服务器。

3. **数据完整性校验**

   HTTPS 使用消息认证码或 AEAD 加密模式对传输数据进行完整性保护。接收方可以校验数据在传输过程中是否被篡改。

   完整性校验的基本思想：

   ```text
   原始数据 -> 摘要/认证标签
   接收方重新计算并比对
   如果结果不一致，说明数据可能被篡改或损坏
   ```

   哈希算法具备输入敏感性：原始数据发生极小变化，计算出的摘要也会显著变化。TLS 在实际实现中不会只依赖普通哈希，而会结合密钥和协议状态进行认证，避免攻击者篡改数据后重新计算摘要。

HTTPS 最终提供的安全目标可以概括为：

```text
加密性：第三方无法直接读懂传输内容
真实性：客户端能确认正在通信的服务器身份
完整性：通信内容被篡改时能够被发现
```
