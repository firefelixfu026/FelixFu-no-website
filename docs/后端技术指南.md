# 后端技术指南

## 1. 后端开发全景

**后端的核心职责**：后端像应用系统的“中枢处理层”，负责接收客户端请求、执行业务逻辑、读写数据库，并把稳定、可理解的结果返回给前端或其他服务。

典型后端请求链路如下：

```text
浏览器 / App / 小程序
  -> HTTP 请求
  -> FastAPI 路由
  -> 参数校验与鉴权
  -> Service 业务逻辑
  -> Repository / ORM
  -> PostgreSQL / Redis / 外部服务
  -> JSON 响应
```

**初学者最先要建立的三个概念**：

- **接口**：前后端约定如何通信，例如 URL、HTTP 方法、请求体、响应体、状态码。
- **数据**：业务最终要落到结构化数据上，例如用户表、订单表、课程表、评论表。
- **边界**：哪些逻辑属于路由层，哪些属于业务层，哪些属于数据库层，边界清晰后项目才容易维护。

一个适合 FastAPI + PostgreSQL 的基础目录结构：

```text
app/
  main.py              # FastAPI 应用入口
  core/
    config.py          # 配置、环境变量
    security.py        # 密码哈希、Token、权限校验
  api/
    routes/
      users.py         # 用户相关接口
      orders.py        # 订单相关接口
  schemas/
    user.py            # Pydantic 请求/响应模型
  models/
    user.py            # ORM 数据模型
  services/
    user_service.py    # 业务逻辑
  repositories/
    user_repo.py       # 数据访问封装
  db/
    session.py         # 数据库连接与会话
```

**为什么要分层**：路由层只处理 HTTP，Service 层处理业务规则，Repository 层处理数据库访问。这样当数据库、接口或业务规则变化时，不需要全项目一起改。

## 2. 接口与协议设计

### 2.1 HTTP 请求与响应

**HTTP 的本质**：客户端发出请求，服务端处理后返回响应。后端开发中的大部分接口，本质都是把业务动作翻译成 HTTP 的请求-响应模型。

常见 HTTP 方法：

| 方法 | 语义 | 后端场景 |
| --- | --- | --- |
| `GET` | 获取资源 | 查询用户、文章列表、订单详情 |
| `POST` | 创建资源或提交动作 | 注册、登录、创建订单 |
| `PUT` | 整体替换资源 | 完整更新用户资料 |
| `PATCH` | 局部更新资源 | 修改昵称、更新订单状态 |
| `DELETE` | 删除资源 | 删除评论、取消收藏 |

状态码要表达处理结果，而不是随手都返回 `200`：

| 状态码 | 含义 | 典型使用 |
| --- | --- | --- |
| `200` | 请求成功 | 查询成功、更新成功 |
| `201` | 资源已创建 | 创建用户、创建订单 |
| `204` | 成功但无响应体 | 删除成功 |
| `400` | 请求格式错误 | 参数类型错误、JSON 格式错误 |
| `401` | 未认证 | 未登录、Token 过期 |
| `403` | 无权限 | 普通用户访问管理员接口 |
| `404` | 资源不存在 | 用户 ID 不存在 |
| `409` | 状态冲突 | 重复注册、库存不足 |
| `500` | 服务端异常 | 未处理异常、数据库故障 |

### 2.2 FastAPI 接口示例

**请求体校验**：FastAPI 通过 Pydantic 模型把“接口文档”和“参数校验”合在一起。字段类型写清楚，错误请求会在进入业务逻辑前被拦截。

```python
from pydantic import BaseModel, EmailStr, Field


class UserCreate(BaseModel):
    email: EmailStr
    password: str = Field(min_length=8, max_length=128)
    nickname: str = Field(min_length=1, max_length=32)


class UserRead(BaseModel):
    id: int
    email: EmailStr
    nickname: str
```

```python
from fastapi import APIRouter, HTTPException, status

router = APIRouter(prefix="/users", tags=["users"])


@router.post("", response_model=UserRead, status_code=status.HTTP_201_CREATED)
async def create_user(payload: UserCreate):
    if await user_exists(payload.email):
        raise HTTPException(
            status_code=status.HTTP_409_CONFLICT,
            detail="email already registered",
        )

    user = await create_user_in_db(payload)
    return user
```

**接口设计建议**：

- URL 使用资源名：`/users/{user_id}`、`/orders/{order_id}`。
- 动作用 HTTP 方法表达：查询用 `GET`，创建用 `POST`，删除用 `DELETE`。
- 响应结构保持稳定，前端才能稳定解析。
- 错误响应要给出可定位的问题，不要直接暴露数据库异常。

### 2.3 CORS 与跨域

**同源策略**：浏览器会限制一个页面访问另一个不同源的接口。源由协议、域名、端口共同决定。

```text
http://localhost:3000
http://localhost:8000

协议相同，域名相同，端口不同 -> 不同源
```

**CORS 的作用**：服务端通过响应头告诉浏览器：“我允许哪些来源、方法、请求头访问我”。

FastAPI 中常见配置：

```python
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],
    allow_credentials=True,
    allow_methods=["GET", "POST", "PATCH", "DELETE", "OPTIONS"],
    allow_headers=["Authorization", "Content-Type"],
)
```

**重要提醒**：如果需要携带 Cookie，不能把 `allow_origins` 简单写成 `["*"]`。带凭证请求必须明确允许具体来源。

## 3. 数据模型与 SQL 基础

### 3.1 为什么需要数据库

**文件存储的问题**：文件适合简单持久化，但当业务需要用户、商品、订单、订阅关系等多类数据时，会遇到查询困难、并发困难、一致性困难。

数据库提供的核心能力：

- **结构化存储**：用表、行、列描述业务实体。
- **查询语言**：用 SQL 表达筛选、连接、聚合。
- **完整性约束**：用主键、外键、唯一约束保护数据质量。
- **事务与并发控制**：多个请求同时读写时保持一致。

### 3.2 表、主键与外键

关系型数据库把数据组织成表：

```sql
CREATE TABLE departments (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE students (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    department_id BIGINT REFERENCES departments(id)
);
```

**主键**用于唯一标识一行数据，通常不应频繁修改。**外键**用于表达表之间的关系，让数据库帮助你维护引用完整性。

外键的价值可以这样理解：

```text
没有外键：
  students.department_id = 999
  departments 表里可能根本没有 999

有外键：
  数据库拒绝无效 department_id
  业务数据不容易变成“孤儿数据”
```

### 3.3 CRUD 与常用查询

```sql
-- 创建
INSERT INTO students (name, department_id)
VALUES ('Alice', 1);

-- 查询
SELECT id, name
FROM students
WHERE department_id = 1;

-- 更新
UPDATE students
SET name = 'Alice Chen'
WHERE id = 1;

-- 删除
DELETE FROM students
WHERE id = 1;
```

连接查询用于整合多张表的信息：

```sql
SELECT s.id, s.name, d.name AS department_name
FROM students AS s
JOIN departments AS d ON s.department_id = d.id
WHERE d.name = 'Computer Science';
```

聚合查询用于统计：

```sql
SELECT department_id, COUNT(*) AS student_count
FROM students
GROUP BY department_id
HAVING COUNT(*) > 10;
```

### 3.4 索引与查询性能

**索引的直觉**：索引像书的目录。没有目录时，要一页一页翻；有目录时，可以先定位范围，再读取数据。

常见索引场景：

- 经常出现在 `WHERE` 条件中的字段。
- 经常用于 `JOIN` 的外键字段。
- 经常用于排序的字段。
- 需要唯一约束的字段，例如邮箱。

```sql
CREATE UNIQUE INDEX idx_users_email ON users(email);
CREATE INDEX idx_orders_user_id ON orders(user_id);
```

**索引不是越多越好**：每次写入、更新、删除都要维护索引。读多写少的字段适合建索引，频繁变化但很少查询的字段不适合乱建索引。

## 4. ORM 与数据库访问

### 4.1 ORM 是什么

**ORM（Object Relational Mapping）**把数据库表映射成程序中的对象，把 SQL 操作映射成方法调用。

它解决的问题：

- 减少重复手写 SQL。
- 用对象表达表结构，提升可读性。
- 通过参数绑定降低 SQL 注入风险。
- 便于把数据库访问集中管理。

但 ORM 不是数据库的替代品。复杂查询、性能优化、事务边界、索引设计仍然需要理解 SQL 和数据库原理。

### 4.2 SQLAlchemy 异步模型示例

```python
from sqlalchemy import String
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column


class Base(DeclarativeBase):
    pass


class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    email: Mapped[str] = mapped_column(String(255), unique=True, index=True)
    password_hash: Mapped[str] = mapped_column(String(255))
    nickname: Mapped[str] = mapped_column(String(32))
```

```python
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine

engine = create_async_engine(
    "postgresql+asyncpg://app:secret@localhost:5432/notebook",
    pool_size=10,
    max_overflow=20,
    pool_pre_ping=True,
)

AsyncSessionLocal = async_sessionmaker(engine, expire_on_commit=False)
```

Repository 示例：

```python
from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession


async def get_user_by_email(db: AsyncSession, email: str) -> User | None:
    result = await db.execute(select(User).where(User.email == email))
    return result.scalar_one_or_none()
```

**参数绑定的重要性**：不要用字符串拼接 SQL。攻击者可能把输入变成 SQL 片段，造成 SQL 注入。ORM 或 SQLAlchemy Core 会把用户输入当作参数，而不是当作 SQL 语法。

## 5. 事务、并发与锁

### 5.1 事务为什么重要

**事务**是一组要么全部成功、要么全部失败的数据库操作。经典例子是转账：

```text
1. A 账户扣 100
2. B 账户加 100

如果第一步成功后系统崩溃，第二步没执行，钱就凭空消失。
事务让这两步绑定为一个整体。
```

ACID 四个特性：

| 特性 | 含义 | 直观理解 |
| --- | --- | --- |
| 原子性 | 全部成功或全部失败 | 不允许半次转账 |
| 一致性 | 操作前后约束成立 | 总金额不变 |
| 隔离性 | 并发事务互不破坏 | 多人同时操作不串账 |
| 持久性 | 提交后结果保存 | 提交成功后数据不丢 |

FastAPI 中的事务示例：

```python
from sqlalchemy.ext.asyncio import AsyncSession


async def transfer(db: AsyncSession, from_id: int, to_id: int, amount: int) -> None:
    async with db.begin():
        from_account = await get_account_for_update(db, from_id)
        to_account = await get_account_for_update(db, to_id)

        if from_account.balance < amount:
            raise ValueError("insufficient balance")

        from_account.balance -= amount
        to_account.balance += amount
```

### 5.2 行级锁 Row-level Lock

**为什么需要锁**：假设商品库存只剩 1 件，两个请求几乎同时下单。如果两个请求都先读到库存为 1，再分别扣减，就可能卖出 2 件。

错误流程：

```text
请求 A 读取库存 = 1
请求 B 读取库存 = 1
请求 A 扣减库存 -> 0
请求 B 扣减库存 -> 0

结果：两个订单都成功，库存数据却只扣了一次
```

行级锁的做法是：当一个事务正在修改某一行时，其他事务必须等待或失败，直到锁释放。

PostgreSQL 常用写法：

```sql
SELECT id, stock
FROM products
WHERE id = 100
FOR UPDATE;
```

SQLAlchemy 示例：

```python
from sqlalchemy import select


async def get_product_for_update(db: AsyncSession, product_id: int) -> Product:
    result = await db.execute(
        select(Product)
        .where(Product.id == product_id)
        .with_for_update()
    )
    return result.scalar_one()
```

下单扣库存：

```python
async def create_order(db: AsyncSession, user_id: int, product_id: int) -> Order:
    async with db.begin():
        product = await get_product_for_update(db, product_id)

        if product.stock <= 0:
            raise ValueError("out of stock")

        product.stock -= 1
        order = Order(user_id=user_id, product_id=product_id)
        db.add(order)
        return order
```

**关键原则**：

- 锁要放在事务里，否则查询结束后锁就没有意义。
- 事务要尽量短，避免长时间占用锁。
- 先锁再判断，不要先判断再锁。
- 多张表加锁时保持固定顺序，降低死锁概率。

### 5.3 隔离级别

隔离级别决定并发事务之间能看到多少彼此的中间状态。

| 隔离级别 | 能解决的问题 | 代价 |
| --- | --- | --- |
| Read Committed | 避免读到未提交数据 | PostgreSQL 默认，适合多数业务 |
| Repeatable Read | 同一事务内多次读取一致 | 更强隔离，可能增加冲突 |
| Serializable | 接近串行执行 | 最严格，吞吐下降更明显 |

初学阶段先记住：**事务越严格，并发越安全，但性能成本越高**。实际项目要根据业务风险选择，而不是一律开最高级别。

## 6. 登录、鉴权与安全

### 6.1 Cookie 与 Session

**Cookie** 是浏览器保存并自动携带的一小段文本。服务端可以通过 `Set-Cookie` 设置 Cookie，浏览器之后访问匹配域名和路径的接口时会自动带上。

常见 Cookie 属性：

| 属性 | 作用 |
| --- | --- |
| `HttpOnly` | 禁止前端 JavaScript 读取，降低 XSS 窃取风险 |
| `Secure` | 只在 HTTPS 下发送 |
| `SameSite` | 限制跨站请求是否携带 Cookie，降低 CSRF 风险 |
| `Max-Age` / `Expires` | 控制过期时间 |
| `Domain` / `Path` | 控制作用范围 |

**Session** 的流程：

```text
用户登录成功
  -> 服务端生成 session_id
  -> session_id 存入 Redis / 数据库
  -> 浏览器保存 session_id Cookie
  -> 后续请求自动携带 Cookie
  -> 服务端查询 session_id 得到用户身份
```

优点是服务端可以主动删除 Session，实现强制下线。缺点是每次鉴权都要查存储，多服务部署时要共享 Session 存储。

### 6.2 Token 与 JWT

**Token** 是服务端签发给客户端的身份凭证。客户端在后续请求中携带 Token，服务端验证后识别用户。

常见携带方式：

```http
Authorization: Bearer <access_token>
```

**JWT** 是一种自包含 Token，通常由三段组成：

```text
header.payload.signature
```

JWT 的优点：

- 服务端可以不查 Session 存储，直接验证签名。
- 适合分布式 API 服务。
- 可以在 payload 中放少量非敏感声明，例如用户 ID、权限范围、过期时间。

JWT 的缺点：

- 签发后在过期前通常不容易主动撤销。
- payload 只是编码，不是加密，不能放密码、手机号等敏感信息。
- Token 泄露后，攻击者可以在过期前冒用。

### 6.3 密码存储

**永远不要明文存密码**。数据库中应该保存密码哈希，而不是原始密码。

推荐思路：

```text
用户密码
  -> 加盐
  -> 慢哈希算法
  -> 保存 password_hash
```

FastAPI 常见写法：

```python
from passlib.context import CryptContext

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")


def hash_password(password: str) -> str:
    return pwd_context.hash(password)


def verify_password(password: str, password_hash: str) -> bool:
    return pwd_context.verify(password, password_hash)
```

**为什么要慢哈希**：普通哈希太快，攻击者拿到数据库后可以高速撞库。bcrypt、argon2 这类算法故意计算较慢，用时间成本降低暴力破解成功率。

### 6.4 CSRF、XSS 与 CORS

**CSRF**：用户已经登录 A 网站，恶意 B 网站诱导浏览器向 A 网站发请求，因为浏览器会自动带 A 的 Cookie，A 可能误以为是用户本人操作。

防护方式：

- Cookie 设置 `SameSite=Lax` 或 `Strict`。
- 关键写操作使用 CSRF Token。
- 后端校验 `Origin` / `Referer`。
- 不把所有跨域来源都放开。

**XSS**：攻击者把恶意脚本注入页面，脚本在用户浏览器中执行。

防护方式：

- 前端输出时转义用户内容。
- Cookie 使用 `HttpOnly`。
- 后端不要把用户输入直接拼进 HTML。
- 配置合理的 Content Security Policy。

**CORS 不是鉴权机制**。CORS 是浏览器约束，不是服务端安全边界。真正的权限仍然要靠 Token、Session、角色权限、资源归属校验。

## 7. 缓存、Redis 与一致性

### 7.1 为什么需要缓存

**缓存是空间换时间**：把高频读取、计算成本高或数据库压力大的数据放到 Redis 这类内存系统中，减少数据库访问。

典型场景：

- 热门文章、热门商品详情。
- 用户会话 Session。
- 验证码、短期 Token。
- 排行榜、计数器。
- 分布式锁。

### 7.2 Cache Aside 模式

最常见的缓存读取流程：

```text
请求数据
  -> 先查 Redis
  -> 命中：直接返回
  -> 未命中：查询 PostgreSQL
  -> 写入 Redis，并设置 TTL
  -> 返回数据
```

Python 示例：

```python
import json


async def get_product_detail(product_id: int):
    cache_key = f"product:{product_id}"
    cached = await redis.get(cache_key)

    if cached:
        return json.loads(cached)

    product = await product_repo.get_by_id(product_id)
    if product is None:
        return None

    data = product.to_dict()
    await redis.set(cache_key, json.dumps(data), ex=300)
    return data
```

### 7.3 缓存一致性

**一致性问题**：数据库更新了，缓存里还是旧数据，用户可能读到过期结果。

常见策略：

| 策略 | 做法 | 适用场景 |
| --- | --- | --- |
| 先更新数据库，再删除缓存 | 写操作成功后让缓存失效 | 常用，简单稳妥 |
| 设置 TTL | 缓存自动过期 | 容忍短暂旧数据 |
| 延迟双删 | 删除缓存、更新数据库、短暂等待后再删一次 | 降低并发读写下的脏缓存概率 |
| 消息队列同步 | 数据变更后异步通知缓存失效 | 更复杂的分布式系统 |

常用写法：

```python
async def update_product(product_id: int, payload: ProductUpdate):
    async with db.begin():
        product = await product_repo.update(product_id, payload)

    await redis.delete(f"product:{product_id}")
    return product
```

**为什么通常删除缓存，而不是直接更新缓存**：删除缓存让下一次读取从数据库重新加载，可以避免多个写请求并发时互相覆盖缓存。

### 7.4 Redis 分布式锁

分布式锁用于“同一时间只允许一个进程执行某段逻辑”。例如定时任务去重、库存扣减保护、避免重复支付回调处理。

基础思路：

```text
SET lock:order:123 random_value NX EX 10

NX: 只有 key 不存在才设置
EX: 设置过期时间，避免服务崩溃后死锁
random_value: 解锁时校验，避免删掉别人的锁
```

释放锁时要保证“校验 value + 删除 key”是原子操作，通常用 Lua 脚本完成。

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end
```

**分布式锁不是万能解法**：数据库行级锁更适合保护数据库内的强一致写操作；Redis 锁更适合跨进程协调。涉及资金、库存等关键数据时，应优先让数据库约束和事务兜底。

## 8. 异步任务与高并发

### 8.1 async/await 的直觉

FastAPI 支持异步视图函数。异步的价值主要在 I/O 场景：等待数据库、Redis、外部 HTTP 接口时，事件循环可以去处理其他请求。

```text
同步阻塞：
  请求 A 等数据库 -> 线程闲等

异步 I/O：
  请求 A 等数据库 -> 事件循环切去处理请求 B
```

适合 `async` 的任务：

- 数据库查询。
- Redis 访问。
- HTTP API 调用。
- 文件、对象存储等 I/O。

不适合直接塞进事件循环的任务：

- 大量 CPU 计算。
- 图像压缩。
- 大模型推理。
- 长时间同步阻塞库。

这些任务应该交给任务队列、进程池或独立服务。

### 8.2 后台任务

FastAPI 的 `BackgroundTasks` 适合简单、短小、失败影响不大的后台动作，例如发送普通通知。

```python
from fastapi import BackgroundTasks


@router.post("/orders")
async def create_order(payload: OrderCreate, tasks: BackgroundTasks):
    order = await order_service.create(payload)
    tasks.add_task(send_order_email, order.id)
    return order
```

如果任务需要重试、削峰、可观测、失败补偿，应该使用 Celery、RQ、Arq 或消息队列。

### 8.3 连接池

数据库连接不是越多越好。连接过多会压垮 PostgreSQL，连接过少会让请求排队。

基本原则：

- 应用侧使用连接池复用连接。
- 不要在每个请求里新建数据库引擎。
- 慢查询会占用连接，拖慢整个服务。
- 长事务会占用锁和连接，应尽量拆短。

## 9. 搜索、倒排索引与向量数据库

### 9.1 为什么 `LIKE '%keyword%'` 慢

普通 B+ 树索引适合前缀、范围、等值查询，但 `LIKE '%keyword%'` 前面有通配符，数据库很难从索引起点定位，只能扫描大量文本。

低效查询：

```sql
SELECT *
FROM documents
WHERE content LIKE '%搜索引擎%';
```

**倒排索引**的思路：

```text
文档 1: 后端 数据库 缓存
文档 2: 数据库 索引 搜索

倒排索引：
后端 -> [文档 1]
数据库 -> [文档 1, 文档 2]
搜索 -> [文档 2]
```

搜索引擎会先分词，再通过词到文档的映射快速定位候选文档。Elasticsearch、OpenSearch 等系统都建立在类似思想之上。

### 9.2 向量数据库

传统数据库擅长精确匹配，向量数据库擅长语义相似度检索。

```text
文本 / 图片 / 音频
  -> Embedding 模型
  -> 高维向量
  -> 相似度检索
  -> 返回语义相近内容
```

常见相似度：

| 方法 | 越大/越小越相似 | 说明 |
| --- | --- | --- |
| 欧式距离 | 越小 | 直接计算空间距离 |
| 内积 | 越大 | 常用于向量检索 |
| 余弦相似度 | 越大 | 关注方向相似度 |
| BM25 | 越大 | 传统全文检索相关性算法 |

KNN 会逐一计算距离，准确但慢。ANN 通过索引减少搜索空间，牺牲少量精确度换取速度。常见 ANN 思路包括哈希、树、图、聚类与倒排结构，其中 HNSW 是工程中很常见的图索引方案。

如果你已经在用 PostgreSQL，可以先了解 `pgvector`：

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE document_embeddings (
    id BIGSERIAL PRIMARY KEY,
    content TEXT NOT NULL,
    embedding vector(1536)
);
```

初学建议：

- 小项目先从 PostgreSQL + `pgvector` 或 Chroma 入门。
- 数据量上百万、并发高、需要复杂过滤时，再考虑 Milvus、Qdrant、Weaviate、Pinecone 等专门系统。
- 向量检索不替代关系数据库，它通常和业务表配合使用。

## 10. 可观测性与故障定位

### 10.1 日志、指标、链路追踪

上线后的服务不能只靠本地调试。可观测性关注三个问题：

| 类型 | 回答的问题 | 例子 |
| --- | --- | --- |
| Logs 日志 | 发生了什么 | 某用户创建订单失败 |
| Metrics 指标 | 系统整体状态如何 | QPS、错误率、P95 延迟 |
| Traces 链路追踪 | 一次请求卡在哪里 | API -> DB -> Redis -> 外部支付 |

基础日志建议：

- 每个请求有 `request_id`，方便串联日志。
- 记录关键业务事件，不要记录密码、Token 等敏感数据。
- 异常日志要包含堆栈和上下文。
- 慢查询、外部接口超时要单独关注。

### 10.2 FastAPI 请求日志中间件

```python
import time
import uuid
from fastapi import Request


@app.middleware("http")
async def request_log_middleware(request: Request, call_next):
    request_id = str(uuid.uuid4())
    start = time.perf_counter()

    response = await call_next(request)

    cost_ms = (time.perf_counter() - start) * 1000
    logger.info(
        "request finished",
        extra={
            "request_id": request_id,
            "method": request.method,
            "path": request.url.path,
            "status_code": response.status_code,
            "cost_ms": round(cost_ms, 2),
        },
    )
    response.headers["X-Request-ID"] = request_id
    return response
```

常见工具组合：

- Prometheus：采集指标。
- Grafana：展示仪表盘。
- OpenTelemetry：统一埋点标准。
- Jaeger：查看分布式链路追踪。

## 11. 支付、Webhook 与幂等性

### 11.1 为什么支付不能只放收款码

收款码适合简单赞助，不适合正式订单系统。订单系统需要处理：

- 订单创建。
- 支付状态回调。
- 退款。
- 重复通知。
- 支付失败和超时关闭。
- 对账。

Stripe、支付宝等支付服务通常通过 **Webhook** 通知服务端支付结果。

```text
用户发起支付
  -> 后端创建支付单
  -> 支付平台处理
  -> 支付平台回调 Webhook
  -> 后端验证签名
  -> 更新订单状态
```

### 11.2 幂等性

**幂等性**指同一个请求执行一次和执行多次，最终结果一致。支付回调必须幂等，因为支付平台可能重复通知。

```python
async def handle_payment_webhook(event_id: str, order_id: int):
    async with db.begin():
        processed = await webhook_repo.exists(event_id)
        if processed:
            return

        order = await order_repo.get_for_update(order_id)
        if order.status != "paid":
            order.status = "paid"

        await webhook_repo.mark_processed(event_id)
```

**关键点**：

- 验证 Webhook 签名，确认来源可信。
- 用事件 ID 或业务单号去重。
- 更新订单时加事务和行级锁。
- 不要在回调里执行不可控的长耗时逻辑。

## 12. 架构模式与工程习惯

### 12.1 配置管理

配置不要硬编码在代码里。数据库密码、密钥、环境标识应从环境变量或配置文件读取。

```python
from pydantic_settings import BaseSettings


class Settings(BaseSettings):
    database_url: str
    redis_url: str
    jwt_secret_key: str
    debug: bool = False


settings = Settings()
```

### 12.2 统一错误处理

业务错误要可预期，系统错误要可观测。

```python
class BusinessError(Exception):
    def __init__(self, code: str, message: str):
        self.code = code
        self.message = message
```

```python
from fastapi.responses import JSONResponse


@app.exception_handler(BusinessError)
async def business_error_handler(_, exc: BusinessError):
    return JSONResponse(
        status_code=400,
        content={"code": exc.code, "message": exc.message},
    )
```

### 12.3 设计模式在后端中的价值

设计模式不是背名词，而是为了让代码更稳定地应对变化。

| 模式 | 后端中的直观场景 |
| --- | --- |
| Adapter 适配器 | 封装 Stripe、支付宝、短信供应商，让业务层不关心第三方差异 |
| Observer 观察者 | 订单支付成功后通知库存、积分、消息模块 |
| Repository | 把数据库访问集中到数据层，避免路由里散落 SQL |
| Dependency Injection | 在测试中替换数据库、缓存、外部 API |

适配器示例：

```python
class PaymentProvider:
    async def create_payment(self, order_id: int, amount: int) -> str:
        raise NotImplementedError


class StripePaymentProvider(PaymentProvider):
    async def create_payment(self, order_id: int, amount: int) -> str:
        return await stripe_client.create_checkout(order_id, amount)


class AlipayPaymentProvider(PaymentProvider):
    async def create_payment(self, order_id: int, amount: int) -> str:
        return await alipay_client.create_trade(order_id, amount)
```

业务层只依赖 `PaymentProvider`，以后换支付渠道时，不需要重写订单逻辑。

## 13. 后端学习检查清单

### 13.1 接口层

- 是否能解释 `GET`、`POST`、`PUT`、`PATCH`、`DELETE` 的区别。
- 是否能为接口选择合理状态码。
- 是否能写清楚请求体、响应体和错误响应。
- 是否理解 CORS 预检请求和 Cookie 跨域限制。

### 13.2 数据库层

- 是否能独立设计主键、外键、唯一约束。
- 是否能写基本 CRUD、JOIN、GROUP BY。
- 是否知道索引适合什么字段。
- 是否理解事务的 ACID。
- 是否知道什么时候要用 `SELECT FOR UPDATE`。

### 13.3 安全层

- 是否避免明文存储密码。
- 是否理解 Session、JWT、OAuth 的区别。
- 是否知道 Cookie 的 `HttpOnly`、`Secure`、`SameSite`。
- 是否能解释 CSRF 和 XSS 的基本防护。

### 13.4 高并发与架构层

- 是否知道缓存命中、缓存穿透、缓存失效的基本处理。
- 是否能解释 Redis 分布式锁的 `NX`、过期时间和随机 value。
- 是否知道 async/await 适合 I/O，不适合 CPU 密集任务。
- 是否能把路由、业务、数据访问分层。
- 是否能通过日志、指标、链路追踪定位线上问题。

**最终目标**：不是记住每个工具的 API，而是理解请求、数据、事务、缓存、安全和可观测性之间的关系。后端系统的可靠性，往往来自这些边界处的细节处理。
