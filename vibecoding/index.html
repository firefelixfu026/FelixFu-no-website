    工科大一生的 Vibe Coding 与 Agent 体系化学习笔记

    这篇笔记不是“AI 写代码工具清单”，而是我作为工科大一学生，尝试把 Vibe Coding、AI Agent、MCP、RAG、SubAgent、Workflow 这些概念放进同一个工程坐标系里。我的目标很明确：不只会让模型写几段代码，而是能理解模型为什么能写、为什么会错、工具如何接入真实环境，以及多智能体系统如何从玩具 Demo 走向可验收的工程闭环。

    1. 范式转变：最后的心法

    1.1 分工重构：我如何理解 Vibe Coding 的核心内核

    Vibe Coding 最容易被误解成“用自然语言让 AI 帮我写代码”。但我越实践越发现，它真正改变的不是输入方式，而是工程分工。

    传统写代码时，我的大脑经常被语法细节、API 记忆、样板代码、重复修改占满。Vibe Coding 把这些低价值摩擦交给模型和工具后，人可以把注意力重新放回“目标是否正确、边界是否完整、工程是否可维护”上。

    我目前把整个系统拆成四个角色：

    1. 人负责目标、判断、验收和取舍 人不是消失了，而是从“代码字符的搬运者”升级成“问题定义者”和“质量裁判”。我需要明确要解决什么问题、什么功能可以先砍掉、什么风险必须兜住、什么输出才算合格。

    2. 模型负责生成、改写、补全和加速重复劳动 大模型擅长从上下文中预测高概率代码形态，适合写脚手架、补测试、改文档、解释报错、迁移风格。但它不是编译器，也不是事实数据库。它的输出必须被运行、测试和审查。

    3. 工具负责连接真实环境 模型本身只会输出 token，真正改变世界的是工具：读文件、改文件、运行测试、查数据库、访问 API、执行命令、打开浏览器。没有工具，模型只是“会说话”；有工具，模型才开始接近“能做事”。

    4. Agent 负责串联多步骤 Agent 的核心不是“更聪明的聊天机器人”，而是带有目标、状态、工具调用、反馈循环的执行系统。它能把“读需求、查代码、设计方案、编辑文件、跑测试、修复失败、总结结果”串起来，形成闭环。

    用一个工程公式概括：

    Vibe Coding = 人类意图编排 + LLM 生成能力 + 工具执行能力 + Agent 多步闭环

    这里的关键痛点是：如果人类意图模糊，模型会把模糊放大；如果工具权限混乱，Agent 会把错误自动化；如果没有验收标准，生成速度越快，技术债堆得越快。

    1.2 角色蜕变：从 Coder 到 Architect

    我以前理解“会编程”，就是会写语法、会调 Bug、会背 API。现在我更愿意把自己训练成一个能用自然语言编排意图的架构师。

    这个转变不是逃避底层，而是把底层知识用在更高杠杆的位置：

    • 写代码时，我不再只问“这一行怎么写”，而是问“这个模块的输入输出边界是否稳定”。
    • 调 Bug 时，我不再只盯着报错文本，而是追踪“状态从哪里被污染、假设在哪里破裂”。
    • 使用 AI 时，我不再把回答当答案，而是把回答当候选实现，需要经过编译、测试、Review 和取舍。

    作为大一学生，我面临的挑战很现实：

    • 基础不牢时容易被模型带偏：模型生成一段看起来很专业的代码，我如果不懂数据结构、网络、操作系统、数据库，就很难判断它是不是在胡编。
    • 工程经验不足时容易过度抽象：AI 很会写复杂架构，但复杂不等于高级。MVP 阶段最重要的是跑通用户价值，而不是提前堆框架。
    • 上下文管理能力不足时容易失控：项目变大后，把整个项目一次性塞给模型不现实。我必须学会切任务、给上下文、写约束、做验收。

    但机遇也很大：

    • 我可以用 AI 快速补齐陌生技术栈的第一版认知。
    • 我可以用 AI 把课程作业、小工具、个人知识库快速产品化。
    • 我可以更早接触工程闭环：需求、实现、测试、部署、文档、评估。

    我的判断是：未来低年级学生的差距，不只在“会不会写代码”，而在“能不能把问题清晰拆解，并驱动 AI 系统稳定地产出工程结果”。

    2. 路线一：如何做好 Vibe Coding（从零到一的工程闭环）

    2.1 大模型原理与协同：Vibe Coding 的起点

    2.1.1 模型为什么能生成代码

    大语言模型的底层目标可以粗略理解为：基于前文上下文，预测下一个 token 的概率分布。代码本质上也是一种高度结构化的语言，具有大量重复模式：

    • 函数签名后面常跟参数校验、核心逻辑、返回值。
    • Web 路由常跟请求解析、服务调用、响应序列化。
    • 测试文件常包含 arrange、act、assert 三段结构。
    • 配置文件常遵循固定 schema。

    模型在海量代码和文本上训练后，学到的是“上下文模式到输出模式”的映射。它并不真正像编译器一样执行代码，也不天然知道项目当前真实状态。它生成代码的能力来自统计规律、语义压缩和上下文对齐。

    这解释了为什么模型对这些任务特别强：

    • 根据已有文件风格补一个相似模块。
    • 根据报错信息推测可能原因。
    • 把自然语言需求翻译成接口、类型、测试。
    • 把重复样板代码批量改写。

    也解释了为什么它在这些任务上容易翻车：

    • 使用并不存在的库函数。
    • 忽略版本差异。
    • 编造配置字段。
    • 忽略项目里的隐藏约束。
    • 在复杂状态流里丢失边界条件。

    2.1.2 模型为什么会产生幻觉

    幻觉不是模型“故意骗我”，而是生成机制的副作用。模型要持续输出一个看起来合理的序列，但“合理”不等于“真实”。

    常见原因有四类：

    1. 训练知识滞后 框架版本更新后，模型可能仍按旧 API 写代码。

    2. 上下文不足 模型没有看到真实文件、配置、依赖版本，就会按常见项目结构猜。

    3. 目标函数偏向流畅 模型优化的是语言连贯性和任务拟合度，不是自动保证事实正确。

    4. 工具反馈缺失 没有运行测试、没有读取文档、没有访问真实环境时，模型无法校正自己。

    所以我的实践原则是：

    模型输出不是答案，而是候选补丁。
候选补丁必须进入工程验证链路：运行、测试、Review、回滚预案。

    2.1.3 多模型协同：一个写，一个审，一个讲

    我现在更喜欢把模型分工，而不是让同一个模型从头包到尾：

    • Coder 模型：负责快速生成代码、补测试、迁移结构。
    • Reviewer 模型：从安全、边界、复杂度、可维护性角度挑刺。
    • Doc 模型：把实现沉淀成 README、接口说明、学习笔记。
    • Research 模型：查官方文档、总结版本差异、给出迁移建议。

    一个简单协同流程如下：

    1. 我写需求和验收标准。
    2. Coder 生成最小实现。
    3. 工具运行格式化、测试、构建。
    4. Reviewer 只看 diff，找 Bug 和遗漏测试。
    5. Coder 根据 Review 修改。
    6. Doc 生成使用说明和变更记录。
    7. 我最终验收，决定合并或回滚。

    这套流程的价值在于：不同模型或不同提示词角色之间形成“制衡”。生成和审查分离，可以降低自我确认偏差。

    2.2 开发工具大全：我们的放大器

    2.2.1 CLI、插件、IDE 的 AI 工具体系

    我把 AI 开发工具分成三层：

    工具层级 典型形态 优势 风险
    CLI Agent Codex、Claude Code 类命令行工具 接近真实工程环境，能读写文件、运行命令、串联任务 权限过大时可能误改文件，需要 Git 和测试兜底
    IDE 插件 Cursor、VS Code AI 插件、JetBrains AI 类工具 和编辑器结合紧，适合补全、解释、局部重构 容易只处理局部代码，看不到完整工程约束
    Web Chat ChatGPT、Claude、Gemini 等网页对话 适合头脑风暴、解释概念、生成草稿 难以直接接入本地真实上下文
    自动化平台 Dify、Coze、n8n、LangGraph Studio 类工具 适合可视化工作流、业务编排、原型搭建 抽象层高，复杂场景可能受限

    我的体会是：工具越靠近真实项目，越需要工程纪律。CLI Agent 很强，但必须配合 Git、测试和明确权限边界。

    2.2.2 MCP：把模型接入外部资源

    MCP（Model Context Protocol，模型上下文协议）可以理解为一种让模型应用统一连接外部工具和数据源的协议。它解决的是“每个 AI 工具都重复写一套插件适配”的问题。

    MCP 的基本结构：

    MCP Client（模型应用）
        |
        | 统一协议
        v
MCP Server（暴露能力）
        |
        +-- Tools：可执行动作
        +-- Resources：可读取资源
        +-- Prompts：可复用提示模板

    三大原语的区别：

    • Tool 动作：模型可以调用的函数，例如查询数据库、创建 issue、读取网页、执行搜索。
    • Resource 资源：模型可以读取的上下文，例如文件内容、数据库记录、API 文档、日志。
    • Prompt 模板：预定义的任务模板，例如代码审查模板、日报模板、SQL 分析模板。

    一个 MCP Server 的价值在于：把外部能力变成结构化接口，而不是让模型在自然语言里猜。

    示例配置可以长这样：

    {
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "./docs"]
    }
  }
}

    初学者真正要注意的是安全边界：

    • 不要给 Agent 默认开放全盘读写。
    • Tool 的参数 schema 要清晰，避免模型传错参数。
    • 高风险操作要有人工确认，例如删除、支付、发布、发邮件。
    • 工具返回结果要结构化，避免把错误文本直接当成功结果。

    2.2.3 Skill：把高频能力封装成固定套路

    Skill 可以理解为“给 Agent 的操作手册”。它通常不是一个大而全的插件，而是某类任务的稳定流程、约束、脚本、模板和参考资料。

    比如一个 code-review Skill 可能包含：

    • Review 优先级：安全、正确性、回归风险、测试缺口。
    • 常用检查命令：npm test、pytest、mkdocs build。
    • 输出格式：先列问题，再列摘要。
    • 项目内约定：不要修改生成文件，不要动用户未授权文件。

    Skill 和 MCP 的区别：

    • MCP 更像“接入能力”：我能调用什么工具、读什么资源。
    • Skill 更像“固化方法”：遇到某类任务时，我应该怎么做。

    我的理解是：MCP 扩展 Agent 的手，Skill 稳定 Agent 的脑回路。

    2.3 意图编排与提示词工程：自然语言编程规范

    Vibe Coding 不是随便说一句“帮我写个网页”。自然语言越像工程规格，模型越容易产出可验收结果。

    我常用的提示词结构：

    目标：
  我想实现什么业务结果，而不是只描述技术动作。

背景：
  当前项目结构、已有模块、依赖版本、用户场景。

输入输出：
  用户输入什么，系统输出什么，异常时怎么处理。

约束条件：
  不能改哪些文件，必须沿用哪些模式，性能和安全要求是什么。

验收标准：
  哪些测试通过，哪些页面可见，哪些命令执行成功，哪些边界情况要覆盖。

交付格式：
  需要代码、说明、测试、文档，还是只要分析结论。

    一个坏提示词：

    帮我做一个 AI 笔记系统。

    一个更工程化的提示词：

    目标：
  在现有 MkDocs Material 项目中新增一篇中文学习笔记，文件放在 docs/vibecoding.md。

内容：
  主题是 Vibe Coding 与 AI Agent 学习路线，必须包含 MCP、RAG、SubAgent、Workflow、DataWhale hello-agents。

约束：
  使用标准 Markdown 标题；核心概念必须用表格；命令和配置必须用代码块；不要修改已有笔记内容。

验收：
  文件能被 MkDocs 正常构建；标题层级清晰；表格语法正确；内容适合个人数字花园长期维护。

    初学者容易踩的坑：

    • 只描述“做什么”，不描述“不要做什么”。
    • 没有给验收标准，导致模型不知道何时结束。
    • 一次塞太多目标，模型开始混合需求。
    • 不告诉模型项目已有约定，结果生成了风格割裂的代码。

    我的经验是：提示词不是玄学，而是“需求文档的压缩版”。写提示词的过程，本质上是在逼自己澄清问题。

    2.4 从 MVP 到迭代开发循环

    2.4.1 MVP 阶段：先跑通价值，不先堆架构

    MVP（Minimum Viable Product，最小可行产品）不是“粗糙产品”，而是用最小成本验证核心假设。

    做 AI 辅助开发时，MVP 阶段最重要的是限制模型发挥范围：

    • 先实现一条最核心用户路径。
    • 先用内存、文件或简单数据库，不急着上复杂基础设施。
    • 先写最关键的测试，不追求覆盖所有边角。
    • 先做可观察日志，方便知道系统到底哪里坏。

    例如我要做一个“AI 论文摘要工具”，MVP 可以只包含：

    1. 上传或粘贴论文文本。
    2. 调用模型生成摘要。
    3. 输出三段结构：研究问题、方法、结论。
    4. 保存一次结果到本地文件。

    暂时不做：

    • 多用户登录。
    • 复杂权限系统。
    • 向量数据库。
    • 自动爬论文。
    • 精美前端。

    这不是偷懒，而是把不确定性压缩到最小。

    2.4.2 幻觉识别与代码审核

    我常用的幻觉检查清单：

    • API 是否真实存在：去官方文档或本地类型定义里查。
    • 依赖是否已经安装：看 package.json、requirements.txt、pyproject.toml。
    • 函数是否被调用到：搜索引用，不只看生成文件。
    • 错误路径是否处理：网络失败、空输入、权限不足、超时。
    • 状态是否一致：缓存、数据库、前端状态是否同步。
    • 测试是否真的覆盖新逻辑：不是只有快照或无意义断言。

    代码 Review 时，我优先看这几类问题：

    1. 正确性：输入输出是否符合需求。
    2. 边界条件：空值、异常、并发、权限。
    3. 安全性：密钥泄露、命令注入、越权访问。
    4. 可维护性：命名、模块边界、重复代码。
    5. 可测试性：是否能通过自动化测试验证。

    2.4.3 “描述-生成-运行-反馈-修改”闭环

    我的 Vibe Coding 开发闭环：

    1. 描述 写清楚目标、上下文、约束、验收标准。

    2. 生成 让模型产出最小改动，不一口气重构全项目。

    3. 运行 运行格式化、类型检查、测试、构建、启动服务。

    4. 反馈 把真实错误日志、失败用例、截图、diff 给模型。

    5. 修改 让模型基于证据修复，不让它凭空猜。

    6. 沉淀 把稳定流程写入脚本、文档、Skill 或 CI。

    这个循环的关键不是“生成”，而是“反馈”。没有反馈，模型只是在猜；有反馈，系统才会逼近正确。

    2.4.4 用 Hooks 自动化重复操作

    Hooks 的意义是：把“每次都应该做”的检查从人脑里拿出来，放进自动化链路。

    典型 Git pre-commit 配置：

    repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-json

    前端项目可以在 package.json 中定义：

    {
  "scripts": {
    "format": "prettier --write .",
    "lint": "eslint .",
    "test": "vitest run",
    "build": "vite build"
  }
}

    然后让 Agent 每次改完都执行：

    npm run format
npm run lint
npm test
npm run build

    MkDocs 项目可以用：

    mkdocs build --strict

    这样做的底层逻辑是：把“模型可能犯错”的不确定性，交给确定性的程序去压制。

    2.5 高级演进：项目变大后的上下文管理与质量控制

    2.5.1 上下文管理

    项目变大后，最大问题不是模型不会写，而是模型不知道该看什么。

    我把上下文分成四类：

    • 任务上下文：这次要改什么，验收标准是什么。
    • 代码上下文：相关文件、接口、类型、调用链。
    • 历史上下文：之前为什么这样设计，哪些坑踩过。
    • 运行上下文：错误日志、测试结果、用户反馈。

    上下文管理的做法：

    1. 用 README、CONTRIBUTING、docs/architecture.md 写稳定规则。
    2. 用清晰目录结构降低模型检索成本。
    3. 每次只提供相关文件，不把无关上下文塞满窗口。
    4. 对长任务做阶段总结，把已完成内容压缩成状态摘要。
    5. 把决策记录写成 ADR（Architecture Decision Record）。

    2.5.2 RAG：让模型先检索再生成

    RAG（Retrieval-Augmented Generation，检索增强生成）的核心思想是：不要让模型只靠参数记忆回答，而是先从外部知识库检索相关材料，再基于材料生成。

    基本流程：

    1. 文档切分成 chunks。
    2. 使用 embedding 模型把 chunks 转成向量。
    3. 用户问题也转成向量。
    4. 在向量数据库中检索相似 chunks。
    5. 把检索结果塞进上下文。
    6. LLM 基于证据回答。

    示意：

    User Query
   |
Embedding
   |
Vector Search
   |
Relevant Docs
   |
LLM Answer with Citations

    RAG 的核心痛点：

    • chunk 太小会丢上下文，太大会引入噪声。
    • embedding 相似不等于语义上真的有用。
    • 检索到了材料，模型也可能忽略或误读。
    • 知识库更新后，索引要同步更新。

    我的实践体会是：RAG 不是“接一个向量库就变聪明”，而是上下文工程。真正难的是文档结构、检索策略、重排序、引用证据和评估。

    2.5.3 SubAgent 与 Agent Team

    当任务复杂到一个上下文窗口塞不下，或者需要多个视角并行处理时，就需要 SubAgent。

    SubAgent 的价值：

    • 上下文隔离：每个子 Agent 只看自己负责的材料，避免主上下文爆炸。
    • 角色隔离：实现、测试、Review、研究可以分开。
    • 并行推进：不同模块可以同时分析或开发。
    • 风险隔离：子 Agent 的输出需要被主 Agent 汇总和审核。

    一个 Agent Team 可以这样分工：

    Planner Agent：拆解任务，制定路线
Coder Agent：实现代码
Reviewer Agent：检查风险和测试缺口
Research Agent：查文档和外部资料
QA Agent：运行测试，复现用户路径
Writer Agent：生成文档和变更说明

    但多 Agent 不是越多越好。初学者最容易犯的错误是把简单任务复杂化。我的判断标准：

    • 任务是否能并行？
    • 子任务之间是否有明确边界？
    • 是否真的需要上下文隔离？
    • 汇总成本是否小于并行收益？

    如果答案是否定的，一个清晰提示词加一个强模型，往往更高效。

    3. 路线二：核心名词概念速通（期末复习与查漏补缺）

    核心名词 技术本质/定义 我的一句话通俗理解 在 Vibe Coding 中的角色
    LLM（大语言模型） 基于大规模语料训练的生成模型，通过上下文预测 token，并在指令微调和对齐后具备对话、推理、代码生成能力。 一个把“上下文模式”压缩进参数里的超级补全器，但不是天然可靠的事实机器。 负责生成代码、解释错误、补文档、提出方案，是 Vibe Coding 的核心生成引擎。
    Function Calling（函数调用） 模型根据用户意图输出结构化函数名和参数，由外部程序真正执行函数并把结果返回模型。 从“只会说”到“能调用工具”的桥梁。 让模型可以查数据库、调 API、跑脚本，把自然语言意图变成真实动作。
    Agent / SubAgent（智能体与子智能体） Agent 是带目标、状态、工具和反馈循环的任务执行系统；SubAgent 是为特定子任务隔离上下文和职责的从属智能体。 Agent 像项目执行者，SubAgent 像被分出去专攻一个模块的同学。 串联多步骤开发流程，SubAgent 用来做并行研究、代码审查、测试验证和上下文隔离。
    MCP 及其三大原语（Tool、Resource、Prompt）与 MCP Server MCP 是标准化模型应用与外部能力连接的协议；Tool 表示动作，Resource 表示可读上下文，Prompt 表示可复用模板；MCP Server 负责暴露这些能力。 给 AI 工具装一个统一插座，让不同数据源和工具不用重复适配。 把文件系统、数据库、搜索、项目文档、固定提示模板接入 Agent，使其能在真实环境中工作。
    Workflow（工作流设计，如 ReAct 范式、可视化编排） 将任务拆成可控步骤、状态转移、工具调用和判断节点；ReAct 通过 Reasoning 与 Acting 交替推进任务。 不是让模型自由发挥，而是给它一条能回退、能观察、能停止的路线。 约束 Agent 的行为边界，让复杂任务从“随机聊天”变成可观察、可调试、可复现的流程。
    LangChain / LangGraph LangChain 提供模型、工具、检索、链式调用等组件；LangGraph 用图结构表达有状态、多步骤、可循环的 Agent 工作流。 LangChain 像零件库，LangGraph 像把零件接成状态机的线路板。 用于快速搭建 RAG、工具调用、单 Agent 和多 Agent 编排，适合从原型走向工程化。
    Skill（封装的高频细粒度能力） 将某类任务的操作规范、脚本、模板、参考资料封装成可复用能力，让 Agent 稳定遵循固定流程。 把“我每次都这么做”的经验写成 Agent 可执行的说明书。 固化代码审查、文档生成、图像处理、测试流程等高频能力，减少重复提示和风格漂移。

    4. 路线三：DataWhale hello-agent 体系化进阶

    注：DataWhale 官方仓库名是 hello-agents，主题是《从零开始构建智能体》。我这里沿用用户常说的 hello-agent 来指代这套学习体系。

    4.1 基础主线：从初识智能体到经典范式

    我理解 DataWhale hello-agents 的价值，是它没有停留在“调用一个 Agent 框架”的表面，而是试图从原理和实践两侧解释智能体系统。

    一条适合初学者的基础主线：

    1. 初识智能体 先回答“Agent 和普通 Chatbot 有什么区别”。Chatbot 主要是对话，Agent 还需要目标、计划、工具、记忆和执行反馈。

    2. 智能体发展史 从符号主义 AI、专家系统、强化学习、LLM 工具调用，到今天的 AI Native Agent。这个脉络能让我明白：Agent 不是凭空出现，而是旧问题在 LLM 时代获得了新接口。

    3. 大语言模型基础 理解 token、上下文窗口、temperature、embedding、指令对齐、工具调用。没有这些基础，很容易把 Agent 的问题全部误判成“模型不够强”。

    4. 经典范式构建 ReAct、Plan-and-Execute、Reflection、Toolformer 思路、Multi-Agent Debate 等范式，本质上都在解决同一个问题：如何让模型在不可靠的生成能力之上，获得可控的推理和行动结构。

    我觉得最重要的一点是：Agent 的智能不是只来自模型本身，而来自模型、上下文、工具、状态和反馈机制的组合。

    4.2 框架与工程实践

    4.2.1 低代码平台搭建智能体的利弊

    低代码平台如 Dify、Coze、n8n 等，适合快速搭原型：

    优点：

    • 上手快，适合验证业务流程。
    • 可视化节点降低入门门槛。
    • 集成常见模型、知识库、插件、触发器。
    • 适合非工程背景同学参与设计。

    缺点：

    • 复杂状态控制受限。
    • Debug 深度不够，很多错误只能看日志猜。
    • 权限、安全、版本管理容易被平台抽象掉。
    • 一旦业务逻辑复杂，节点图可能变成新的“意大利面代码”。

    我的选择是：低代码平台适合验证想法，代码框架适合沉淀能力。前者用于快，后者用于稳。

    4.2.2 主流框架开发实践

    主流 Agent 框架大致解决这些问题：

    • 模型调用封装。
    • Prompt 模板管理。
    • Tool schema 定义。
    • 记忆与检索。
    • 状态流转。
    • 多 Agent 协同。
    • 观察日志和评估。

    以 LangChain / LangGraph 为例：

    • LangChain 更像组件库，帮我快速接模型、工具、文档加载器、向量库。
    • LangGraph 更像状态机框架，适合表达循环、分支、人工审批、多 Agent 协作。

    一个极简 Agent 工作流可以抽象成：

    while not done:
    thought = llm.plan(state)
    action = choose_tool(thought)
    observation = tool_call(action)
    state = update_state(state, observation)
    done = should_stop(state)

    这个伪代码暴露了 Agent 的核心工程问题：

    • state 怎么设计？
    • choose_tool 如何避免误调用？
    • tool_call 失败怎么重试？
    • should_stop 如何防止无限循环？
    • 中间过程如何记录，方便复盘？

    4.2.3 构建自己的 Agent 框架

    我认为低年级同学至少应该手写一个玩具 Agent 框架。不是为了替代成熟框架，而是为了摸清底层结构。

    最小 Agent 框架包含：

    1. LLMClient：封装模型请求。
    2. ToolRegistry：注册可调用工具。
    3. PromptBuilder：组装系统提示、任务、工具描述、历史状态。
    4. AgentLoop：执行思考、工具调用、观察、停止判断。
    5. MemoryStore：保存短期历史和长期记录。
    6. TraceLogger：记录每一步输入输出。

    目录结构可以这样设计：

    mini-agent/
  agent/
    loop.py
    prompts.py
    tools.py
    memory.py
    tracing.py
  examples/
    travel_assistant.py
  tests/
    test_tools.py

    手写一次之后，再用 LangChain、LangGraph、AutoGen、CrewAI 等框架，我就更清楚它们到底替我封装了什么，也更能判断什么时候该用框架，什么时候该自己写控制逻辑。

    4.2.4 智能体性能评估：如何判定一个 Agent 真的变聪明了

    Agent 评估比普通模型评估更复杂，因为它不只输出文本，还会调用工具、改变状态、执行多步骤任务。

    我会从五个维度评估：

    评估维度 关注问题 示例指标
    任务成功率 最终是否完成目标 成功/失败、人工评分
    工具调用质量 是否选对工具、参数是否正确 工具调用准确率、无效调用次数
    成本与效率 token、时间、API 调用是否可接受 平均耗时、平均 token、重试次数
    稳定性 同一任务多次运行是否一致 方差、失败复现率
    安全性 是否越权、泄露、误操作 权限违规次数、高风险动作拦截率

    评估集应该包含：

    • 正常任务。
    • 边界任务。
    • 恶意输入。
    • 工具失败。
    • 信息不足。
    • 需要人工确认的任务。

    我的体会是：没有 Eval 的 Agent 只能算 Demo。真正的智能提升，必须能在固定任务集上被测量。

    4.3 记忆、检索与通信

    4.3.1 Memory & Retrieval

    Agent 的记忆可以分成几类：

    • 短期记忆：当前对话和当前任务状态。
    • 长期记忆：用户偏好、历史任务、项目规范。
    • 情景记忆：某次具体事件的上下文。
    • 语义记忆：可被检索的知识片段。
    • 程序性记忆：固定操作流程，可以沉淀成 Skill。

    记忆系统的难点不是“存下来”，而是“什么时候取出来、取多少、信不信”。

    一个合理检索流程：

    1. 根据当前任务生成检索 query。
    2. 检索项目文档、历史记录、代码片段。
    3. 对候选结果重排序。
    4. 过滤过期或低相关内容。
    5. 把结果以结构化形式放进上下文。
    6. 要求模型引用依据，不允许无证据扩写。

    4.3.2 Context Engineering：上下文工程

    上下文工程是我认为 Agent 系统里最容易被低估的部分。它不是简单地“塞更多内容”，而是设计模型在每一步到底该看到什么。

    上下文应该包含：

    • 当前目标。
    • 已知事实。
    • 可用工具。
    • 禁止行为。
    • 当前状态。
    • 最近观察。
    • 验收标准。

    上下文不应该随便包含：

    • 无关历史对话。
    • 大量重复代码。
    • 未验证的猜测。
    • 过期文档。
    • 不必要的敏感信息。

    一个好的 Agent 不是记忆无限，而是检索克制。

    4.3.3 智能体通信协议

    多 Agent 协同时，最大风险是彼此说的话不可解析。自然语言太自由，容易遗漏关键信息。

    我倾向于让 Agent 之间用结构化消息通信：

    {
  "sender": "reviewer",
  "receiver": "coder",
  "task_id": "fix-login-state",
  "message_type": "review_findings",
  "severity": "high",
  "findings": [
    {
      "file": "src/auth/session.ts",
      "issue": "logout only clears local state, but token remains in storage",
      "expected_fix": "clear persistent token and add regression test"
    }
  ]
}

    这类协议至少要定义：

    • 谁发给谁。
    • 针对哪个任务。
    • 消息类型是什么。
    • 需要对方做什么。
    • 成功和失败如何返回。

    多 Agent 通信的底层问题，其实很像分布式系统：状态一致性、消息格式、超时、重试、冲突解决、最终汇总。

    4.4 综合案例演练

    4.4.1 智能旅行助手

    智能旅行助手看起来简单，其实是一个很典型的 Agent 案例。

    用户目标：

    帮我规划 5 天东京旅行，预算 8000 元，偏技术文化、动漫、电子产品，不要太赶。

    Agent 需要做的事情：

    1. 解析用户偏好和硬约束。
    2. 查询机票、酒店、天气、交通、景点开放时间。
    3. 生成候选路线。
    4. 估算预算。
    5. 检查每天行程是否过载。
    6. 根据用户反馈修改。
    7. 输出可执行计划。

    涉及的工具：

    • 搜索工具。
    • 地图 API。
    • 天气 API。
    • 日历工具。
    • 汇率工具。
    • 文档导出工具。

    关键痛点：

    • 外部信息会变化，必须实时检索。
    • 用户偏好可能隐含冲突，例如预算低但酒店要求高。
    • 工具返回数据格式不统一。
    • 最终结果不是“文字好看”，而是能不能真的按计划走。

    这个案例让我明白：Agent 的难点不是写一段行程文案，而是把不确定信息、用户偏好和工具反馈整合成可执行计划。

    4.4.2 赛博小镇：Generative Agents

    Generative Agents 的经典想法是：让多个虚拟角色生活在一个模拟环境中，每个角色有记忆、计划、反思和交互。

    一个“赛博小镇”可以包含：

    • 多个居民 Agent。
    • 每个居民有身份、目标、作息、社交关系。
    • 环境有地点、时间、事件。
    • Agent 根据记忆和当前观察决定行动。
    • 行动反过来改变环境和他人记忆。

    核心机制：

    1. 观察 Agent 看到环境事件和附近角色行为。

    2. 记忆写入 把重要事件写入长期记忆。

    3. 检索 根据当前情境取回相关记忆。

    4. 反思 从多条记忆中总结更高层次的信念。

    5. 计划 生成当天或当前时段行动计划。

    6. 行动 与环境或其他 Agent 交互。

    多智能体协同的未来，我认为会出现在这些方向：

    • 软件工程中的 Agent Team。
    • 游戏 NPC 和虚拟社会模拟。
    • 科研中的自动假设生成与实验规划。
    • 企业流程中的自动协作助手。
    • 个人数字花园中的长期学习伙伴。

    但风险也很明显：

    • Agent 之间可能传播错误信息。
    • 多轮交互后状态难以解释。
    • 成本快速上升。
    • 评估和安全边界更难。

    所以多智能体不是“多开几个模型”这么简单，而是一个系统工程问题。

    5. 个人推荐学习顺序与下一阶段规划

    5.1 Vibe Coding 实用路线

    这条路线适合想快速提升个人项目开发效率的同学。

    1. 原理 学 LLM 基础、上下文窗口、token、幻觉、工具调用。目标是知道模型为什么能写代码，也知道它为什么不能盲信。

    2. 工具 熟悉 CLI Agent、IDE 插件、Web Chat。先用 Git 管住风险，再让 AI 改代码。

    3. 提示词 训练自己写目标、上下文、约束、验收标准。把自然语言当工程规格写。

    4. MVP 每次只做最小可行功能，先跑通核心路径。

    5. 迭代循环 固化“描述-生成-运行-反馈-修改”闭环。让测试、格式化、构建成为默认动作。

    6. RAG / Team 项目变大后引入 RAG 做知识检索，用 SubAgent 做上下文隔离，用 Agent Team 做并行任务。

    我给自己的阶段目标：

    • 第 1 周：用 AI 辅助完成 3 篇高质量 MkDocs 笔记。
    • 第 2 周：做一个课程资料 RAG 问答 Demo。
    • 第 3 周：给 Demo 加测试、日志和简单评估集。
    • 第 4 周：尝试把代码生成、Review、文档生成拆成 Agent Team。

    5.2 智能体系统研究路线

    这条路线适合想深入 Agent 底层机制的同学。

    1. LLM 理解生成、上下文、embedding、对齐和推理局限。

    2. Function Calling 学会定义工具 schema，让模型输出结构化调用，而不是自然语言猜测。

    3. Agent 手写最小 Agent Loop：plan、act、observe、update、stop。

    4. MCP 理解 Tool、Resource、Prompt 和 MCP Server，尝试接入本地文件或知识库。

    5. Workflow 学 ReAct、Plan-and-Execute、Reflection、Human-in-the-loop。重点理解状态机和停止条件。

    6. 框架 使用 LangChain / LangGraph 搭建 RAG、工具调用和多步骤 Agent，理解框架抽象背后的控制流。

    7. 多代理 学 Agent 通信、任务分解、角色隔离、冲突处理和评估。

    下一阶段我最想死磕的三个问题：

    • Agent 为什么会失控 从工具权限、上下文污染、停止条件、错误重试四个角度分析。

    • RAG 为什么检索到了还答错 从 chunk、embedding、rerank、prompt 注入、证据引用角度复盘。

    • 多 Agent 如何评估 不只看最终回答，而要记录每一步工具调用、通信消息、状态变化和成本。
